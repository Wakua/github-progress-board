# マイルストーンのガントチャート

開発担当者と検証担当者向けに、GitHubの計画から依存関係、クリティカルパス、期日との差を確認する要件を定める。
この文書を使い、日程計算と画面の受入条件を確認できる。
対象はGitHubで計画するプロジェクトであり、手動計画のガント表示、自動での担当・Iteration変更、変更シミュレーションは含めない。
実装状況は[開発と検証](development.md#実装状況)を参照する。

## 目的

利用者がマイルストーンの期日に向けて、何を優先し、どの計画を見直すべきか判断できるようにする。
期日が表す完了の範囲は[リリースの作業規則](../AGENTS.md#issueとgithub-project)に従う。

## 確認できること

| 要件 | 確認できること |
| --- | --- |
| 期間と期日 | マイルストーンの期日と、各作業の計算上の開始・完了を同じ時間軸で確認できる |
| 表示単位 | 時間軸を月・週・日へ切り替え、見たい期間の広さに合わせて日程と依存関係を確認できる |
| 依存関係 | 着手を待たせる前提と、その作業の遅れが影響する後続作業をたどれる |
| クリティカルパス | 計算上の完了日を左右する作業の連なりを確認できる。複数ある場合はすべて識別できる |
| 作業の余裕 | 各作業をどれだけ遅らせると、マイルストーンの計算上の完了が遅れるか確認できる |
| 期日との差 | 計算上の完了と期日の間の余裕・超過を、平日の日数で確認できる |
| 進捗と担当 | 作業進捗率、残り作業量、担当と作業の重複を確認できる |
| 計算の根拠 | 使用したデータの取得時点、計算の基準日、計算できない理由を確認できる |

表示対象は開いているマイルストーンとし、期日が未設定のものも含める。
期日がなければ「期日未設定」、対象作業がなければ「作業未登録」と示す。
閉じたマイルストーンは表示しない。

作業から詳細とGitHubの対象Issueを開けるようにする。
既存の見積合計による「最長の流れ」を、クリティカルパスとして表示しない。
既存の作業分類と計算上の開始が異なる場合は、日程に使った前提を確認できるようにする。

### 時間軸の表示単位

時間軸は月・週・日を切り替えられるようにし、選択中の単位と表示期間を示す。
切替では目盛りと棒の縮尺を変え、日程、作業進捗率、依存関係、余裕、クリティカルパス、期日差は変更しない。
月表示では年月、週表示では各週の期間、日表示では日付と曜日を確認できる。
短い棒の中に文字が収まらない場合も、作業の日数と開始・完了を確認できるようにする。

月や週への表示切替で、計算上の日数を月数・週数へ丸めない。
月の日数や年の境界は暦に従い、土日を含む暦上の期間と、[日程計算に使う平日](#基準日と平日)を区別する。

## 計算する作業と依存関係

マイルストーンに属する作業Issueから前提をたどり、計算対象を決める。
作業の単位は[親子Issue](specification.md#親子issue)で定める作業Issueとし、集約用IssueのEstimateは[集計の規則](specification.md#表示ルール)に従う。

前提はGitHubのblocked byを使い、前提の完了後に後続が着手する関係として扱う。
開始の同時指定や、依存関係自体への待ち日数の設定は扱わない。
別のマイルストーンやrepositoryの未完了の前提も含める。

依存関係に集約用Issueが含まれる場合は、配下の最下位の作業Issueまで展開する。
集約用Issueを前提にする後続は、配下のすべての作業Issueの計算上の完了を待つ。
集約用Issue自身に登録された前提は、配下の各作業Issueの前提として適用する。
集約用Issue自身の開閉やProjectのフィールドでは日程を決めず、各作業Issueの情報を使う。

配下がすべて完了済みなら、その集約用Issueによる日程上の待ちはない。
この計算によってGitHubの開閉や既存の[作業分類](specification.md#githubから表示する計画)は変更しない。
展開後の情報不足と循環は、[情報不足と不整合](#情報不足と不整合)に従う。

レビュー、承認、マージに必要な期間は、実装と分けた作業Issueとして、担当、Estimate、Iteration、進捗率、依存関係を持つ。
実装のEstimateに含めていた同じ作業量は、分割時に重複を解消する。
レビュー・承認を待つ期間に一律の見積を自動設定しない。

## 作業進捗率

GitHub Projectの数値フィールド「作業進捗率」に、現在のEstimateで見積もった作業量のうち終わった割合を保存する。
値は0〜100の整数とし、未入力、範囲外、小数は計算に使わない。
未入力を0%と推定しない。

担当AIは、実装・検証など作業の区切りで、完了した内容と残る内容を根拠に更新する。
更新の根拠は、対象Issueのコメントに成果への参照とともに残す。
日が経過しただけでは進捗率を変更しない。
作業追加や差戻しがあれば、現在のEstimateと進捗率を見直し、変更理由を記録する。
当初の見積は変更記録に残す。

未完了作業の残り作業量は、`現在のEstimate × (1 − 作業進捗率 / 100)`で求める。
計算の途中で作業単位の日数を整数へ切り上げない。
完了した作業は、既存の[GitHubの作業分類](specification.md#githubから表示する計画)に従い、残り作業量を0とする。

進捗更新で変更できる範囲は[正本と更新の範囲](#正本と更新の範囲)に従う。
実装の作業進捗率が100%でも、後続のレビュー・承認が残ればマイルストーンの計算は続く。
作業進捗率が100%のまま未完了の作業は、その状態も確認できるようにする。

手動計画の[完了条件の達成率](specification.md#表示ルール)は条件数の割合であり、作業進捗率へ転用しない。
既存の未完了Estimateの合計・終了率・担当別の負荷は、その定義を維持する。
ガントチャートの残り作業量と、未完了作業のEstimate全額を足した値は区別して表示する。

## 日程の計算

### 基準日と平日

計算の基準日は、[日付と平日の規則](specification.md#上限と超過量)で求める今日とする。
基準日が平日なら、その日の開始から計算する。
土日なら次の平日の開始から計算する。
時刻に応じた当日の残り稼働時間の按分は行わない。

作業量の日数換算は[Estimateの定義](specification.md#表示ルール)に従う。

未完了作業の開始は、基準日、割り当てたIterationの開始日、すべての未完了の前提の計算上の完了のうち、最も遅い時点とする。
Iterationの開始日が土日なら、次の平日の開始を開始条件に使う。
Iterationの開始日前には着手しない。
Iterationの終了日を越える計算結果は切り詰めず、割当期間からのはみ出しとして示す。
日程は、登録された前提が終わり次第着手する計画上の値であり、実際の着手・完了の記録とは区別する。

### クリティカルパスと余裕

依存関係と開始条件から各作業の最も早い開始・完了を求める。
対象マイルストーン内の作業のうち、最も遅い完了をマイルストーンの計算上の完了とする。

この完了を遅らせない最も遅い開始・完了を、後続作業から逆順に求める。
作業の余裕は、最も遅い開始と最も早い開始の差とする。
余裕が0の未完了作業とそのつながりを、クリティカルパスとして識別する。
期日までの余裕を、作業の余裕に加算しない。

マイルストーンの期日はその日の終了として扱い、計算上の完了との間に残る、または超える平日の日数を求める。
週末に当たる期日を勝手に変更しない。
期日が未設定でも作業の日程とクリティカルパスは計算し、期日との差を未算出として示す。
閉じたマイルストーンと、対象作業のないマイルストーンは、将来の完了見込みを計算しない。

日数の表示は小数第2位までとし、第3位以下を四捨五入して末尾の0を省く。
0でない値が丸めると0になる場合は「0.01日未満」と示す。
余裕・超過の区別とクリティカルパスの判定には、丸める前の値を使う。

### 担当の重複

同じ担当の作業区間が重なる場合は、該当する作業と期間を警告する。
一つの作業の完了と次の作業の開始が同じ時点なら、重複とはしない。
残り作業量が0の作業は、重複区間を持たない。

担当の重複によって作業を自動で後ろへずらしたり、担当・Iterationを変更したりしない。
クリティカルパスは担当の競合を解消する前の依存関係に基づくものとして扱う。
重複がある計画では、担当の調整が必要であることを完了見込みとともに示す。
担当が不明な作業と、選択したプロジェクト外の作業量は、重複を確認できない範囲として示す。

## 正本と更新の範囲

担当、Estimate、Iteration、Status、作業進捗率は、利用者が指定したGitHub Projectを正本とする。
複数Projectに登録された作業は、計算に使うProjectを特定し、異なるProjectのフィールドを混ぜない。
マイルストーンと依存関係はGitHubのIssue情報を正本とする。

計算に使う作業と前提は、repositoryの内外を問わず、開閉、子Issue、依存関係と、出典Projectの上記フィールドを取得する。
集約用Issueは、最下位の作業Issueを特定できるまで子Issueを取得する。
外部の前提の出典Projectを特定できない場合や、必要情報を取得できない場合は、[情報不足と不整合](#情報不足と不整合)に従う。

担当AIによる進捗の更新は、指定されたProject内の担当作業の作業進捗率、見直しが必要なEstimate、対象Issueの根拠コメントを対象とする。
この進捗更新を理由に、期日、担当、Iteration、Status、Issueの開閉、受入完了を自動変更しない。

初期設定を担当する人またはAIが、指定されたProjectに新フィールドを作成する。
既存の未完了作業は、その担当者が完了した内容と残る内容を確認して初期値と根拠を入力し、未着手と確認した作業に0を入力する。
確認できない作業は未入力のままにし、未入力を理由とする計算の制限を維持する。
初期設定後に新しい作業Issueを登録する人またはAIは、担当、Estimate、Iterationとともに、着手前の作業進捗率0を入力する。
既に作業を始めたIssueを登録する場合は、担当者が確認した作業進捗率と根拠を入力する。

ボードはsnapshotを読み取り、日程を再計算する。
snapshotの取得・取込からGitHubへ書き戻さない。
更新・再取得に失敗した場合の保持は[保存済みデータの保持](specification.md#保存済みデータの保持)に従う。

## 情報不足と不整合

必要なEstimate、作業進捗率、Iterationの開始日、前提の情報が不足する作業は、具体的な不足項目を示す。
その作業と影響を受ける後続の確定した日程を表示しない。
対象に不足があるマイルストーンは、完了見込みとクリティカルパスを確定できないことを示す。
既知の作業の表示と依存関係の確認は続ける。

依存関係の循環を検出したら、循環する作業を示し、その影響範囲の計算を止める。
無関係なマイルストーンの計算は続ける。
情報不足、循環、複数Projectの出典未確定を、0日や前提なしとして補わない。

## 受入条件

以下は架空の計画を使う検証例である。
特記しない作業は未着手、必要情報がすべてあり、同じ平日の開始から着手でき、別担当で並行できるものとする。
日数は基準日から数えた平日の日数で示す。

| 条件 | 期待する結果 |
| --- | --- |
| Aが2pt、A完了後のBが3pt、独立したCが4pt。BとCの完了が必要 | 完了まで5日、A→Bがクリティカルパス、Cの余裕は1日 |
| 上の例で期日まで7日ある | 作業の余裕は変わらず、マイルストーンの期日までの余裕は2日 |
| 上の例で期日まで3日しかない | 完了見込みは5日で、期日を2日超過する |
| 上の例でCを5ptにする | A→BとCの両方をクリティカルパスとして示す |
| 見積5pt、作業進捗率60%の作業 | 残り作業量は2ptとなり、残りの計算期間は2日 |
| 0.5ptのAの後に0.5ptのBがある | 合計1日となり、各作業を1日に切り上げない |
| 金曜の開始から2ptの作業を始める | 金曜と翌月曜を使い、翌月曜の終了が完了となる |
| 土曜が基準日で、1ptの作業を始める | 翌月曜の開始から計算し、その終了が完了となる |
| 月曜が基準日で、Iterationが翌週月曜から始まる2ptの作業 | 翌週火曜の終了が完了となり、基準日から7日となる |
| 金曜が基準日で、Iterationが翌土曜から始まる1ptの作業 | 翌月曜の開始から計算し、その終了が完了となる |
| 完了まで1.5日の作業がある | 日数は「1.5日」と表示し、2日に丸めない |
| 計算上の超過が0.004日となる | 「0.01日未満」の超過として示し、超過なしにしない |
| 開いたマイルストーンに期日がなく、2ptの作業がある | 表示対象に含め、完了まで2日とクリティカルパスを示し、期日は未設定とする |
| 閉じたマイルストーンがある | ガントチャートに表示せず、将来の完了見込みを計算しない |
| 依存のない作業の担当が同じで、区間が重なる | 両作業を警告し、日程を自動変更しない |
| 実装が100%で、後続の承認が1pt残る | 実装の残りは0ptだが、承認の1日をマイルストーンの完了までに含める |
| 別マイルストーンの前提が2pt、その後の対象作業が1pt | 前提を含めた3日を計算する |
| 親Pの配下に独立したAが2pt、Bが3ptあり、Tが1ptでPを待つ | Tは3日後に開始し、全体は4日となる。PのEstimate、進捗率、Iterationは計算に不要 |
| 上のPがClosedでも、AとBは未完了 | 同じ4日となり、親の開閉で配下を計算から除外しない |
| 上のAとBが中間の集約用Issueの配下にある | 最下位まで展開して同じ4日となり、中間のEstimateも加算しない |
| 上のP自身が1ptのQを待つ | AとBはQの完了後に開始し、Tの完了まで5日となる |
| PはOpenだが配下はすべて完了し、1ptのTがPを待つ | Pによる日程上の待ちはなく、Tは1日で完了する。Pの開閉とTの作業分類は変えない |
| Pの配下を取得できない、または配下のAがPを待って展開後に循環する | 不足または循環を示し、影響範囲の計算を止める |
| 見積、進捗率、Iteration、外部の前提情報のいずれかが足りない | 不足を示し、影響範囲とマイルストーン全体の計算を確定しない |
| AがBを待ち、BがAを待つ | 循環する両作業を示し、影響範囲の計算を止める |
| GitHubの作業進捗率が更新されて再取得に成功する | 同じ規則で日程、余裕、クリティカルパスを再計算し、GitHubへ書き戻さない |
| 初期設定後に未着手の作業を登録する | 登録者が作業進捗率0を入力し、再取得後は未入力として扱わない |
| 初期設定時に既存作業の進み具合を確認できない | 未入力を維持し、マイルストーンの計算を確定しない |

画面の受入では、表示単位を切り替える、依存関係をたどる、クリティカルパスと警告を確認する、作業の詳細・GitHubへ移る操作を実際に行う。
表示単位は日→週→月→日の順に操作し、選択状態・表示期間・目盛りの変化と、[切替で保持する計算結果](#時間軸の表示単位)を照合する。
金曜開始の2pt、小数日数、月・年境界、土日の期日を含むケースでも照合し、短い棒の作業日数と開始・完了を確認する。
操作前後を[UI設計の規則](../AGENTS.md#ui設計)に従って確認する。
