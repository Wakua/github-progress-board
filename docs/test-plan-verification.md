## 保存とAPI

`node --test tests/test-plan-store.test.mjs tests/test-plan-api.test.mjs` の21試験が成功した。

| 確認対象 | 条件と結果 |
| --- | --- |
| ケースDBの移行 | 版1から版2へ追加し、ケース・受付記録の全列が一致。移行途中の失敗はテーブル追加と版変更を戻す |
| 初期値 | ケースと指定した条件の組だけを作る。全件Not Runで、実施者・実施日時・記録日時はNULL |
| 対象の保護 | 新規追加はActiveだけ。記録済みのケース除外、条件の除外・書換え・ID差替えを拒否 |
| 履歴 | ケース・条件・対象版・担当・計画項目・状態を変更前後とともに保存。除外後も履歴から元の対象を参照できる |
| 完了と再開 | Not Runを残した完了は拒否。未解決の結果は確認後に完了し、再開しても結果と履歴を保持 |
| 下書き削除 | 結果のないDraftだけを論理削除。ケース本体・ID・実施単位・履歴は保持。削除の再送は二重処理しない |
| 並行更新 | 古い更新番号には409と最新内容を返し、入力とDBを上書きしない |
| 失敗と再送 | 書込みロック・途中の保存失敗を起こし、計画・実施単位・履歴・受付記録が一緒に戻る。復旧後の再試行が成功 |
| 応答断 | サーバー確定後の応答断から同じ受付キーで再試行し、更新番号と履歴を増やさない。再起動後の再送も保持 |
| ローカル境界 | 他Origin、専用ヘッダーなし、不正な本文、結果入力APIへの要求を拒否 |

全体の `npm test` は856試験成功、`npm run check` と `npm run build` も成功した。

## 実画面の操作

担当者と管理元が、別の確認用計画を操作した。
以下はブラウザー操作の記録であり、利用者による製品受入ではない。

| 操作 | 確認した結果 |
| --- | --- |
| 空の必須入力で次へ進む | 計画名の入力が必要と表示し、作成しない |
| Windows 11/共通とiOS 18/iPhoneを指定 | 条件の組を2件として保持 |
| 通知1件を個別選択し、予約カテゴリの3件を一括選択 | 4ケース×2条件、Not Run 8件を表示して保存。ページ再読込み後も保持 |
| 計画保存後にカード決済のケースを追加し、macOS条件を追加 | 未実施が8→10→15件になり、担当と既存の組を保持 |
| 記録済み対象のケース・条件を開く | 記録済みの対象は「外す」が無効。未実施のiOS条件とケースだけを外してFailedを保持（管理元） |
| 警告がある計画を完了 | Failed・Blocked・Skipped・再テスト待ち各1件を表示。確認チェック前は完了できず、確認後に完了（管理元） |
| 完了した計画を再開 | In Progressへ戻り、完了・再開の履歴と結果を保持（管理元） |
| 下書きの削除を開きEscapeで戻る | 削除せず元の操作へ戻る（管理元）。実削除の永続化は上記DB/API試験で確認 |
| 担当Aを保存 | ケースごとの担当を保存し、元の担当ボタンへフォーカスが戻る |
| 編集をEnterで開き、Tab、Escapeを使う | 計画名→対象版へ移動し、Escapeで元の「編集」ボタンへ戻る |
| 一つの確認用計画にだけ保存失敗を起こす | 版1.4.1の入力を保持し、成功とは表示しない。原因を取り除いて「再試行」すると保存できる |
| 保存失敗後に版を1.4.2から1.4.3へ変更 | 古い入力の「再試行」が消え、復旧後の「保存」で1.4.3を保持 |
| 390×844で一覧を開閉する | 横はみ出しなし。管理元が指摘した見出し・操作語の途中折返しを修正し、担当と管理元で再確認 |

保存失敗の検証用トリガーは解除済みである。
計画の実削除を管理元の画面確認で実行したとは扱わない。
