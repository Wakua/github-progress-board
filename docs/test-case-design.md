# テストケース作成の方針

対象読者は、テストケースを作るスキルの作成者と、スキルの出力を確認するテスト担当者。
対象範囲は、テストレベルごとに確かめる仕様、テスト技法の使い分け、良いテストケースの基準、ケースを導く手順、出力の形式。
読むと、スキルがどの順序でケースを導き、どの時点で人が確認し、出力をどの基準で点検するかを確認できる。

範囲外は、スキルの実装、テスト管理ツールへの取り込みの操作、自動テストのコード生成。

## 位置づけ

スキルはテスト管理ツールの機能ではなく、ツールの外でテストケースの案を作る手順とする。
テスト担当者は、出力を確認してから、[テストケースの登録・編集](test-case-editor.md)でツールに登録する。

## テストレベル

テストレベルごとに、確かめる仕様を分ける。
スキルは、統合テストとシステムテストのケースを作る。

| テストレベル | 確かめる仕様 | 主な観点 | スキルの扱い |
| --- | --- | --- | --- |
| 単体（コンポーネント） | 内部仕様。関数やモジュールの設計 | 分岐、境界、例外 | 対象外。開発者が自動テストで確かめる |
| 統合 | 外部仕様。画面、API、連携先とのやりとり | 受け渡すデータ、連携先が失敗したときの動作、操作の順序 | ケースを作る |
| システム | 要求仕様。利用者が目的を達成できるか | 利用場面の通しの操作、性能や使いやすさ | ケースを作る |
| 受入 | 利用者の業務 | 実際の運用で使えるか | 観点の案だけを出す |

「結合テスト」と「統合テスト」は同じテストレベルとして扱う。
同じ内容を複数のテストレベルで確かめない。
ほかのテストレベルで確かめる観点は、どのレベルで確かめるかを書いて対象外にする。

## ブラックボックスとホワイトボックス

ケースは、仕様から導くブラックボックスのテストとして作る。
コードの分岐からケースを作ると、実装を変えるたびにケースも変わり、仕様にあるのに実装されていない動作を見つけられないためである。

コードの構造は、次の用途に限って使う。

- 単体の自動テストで測った分岐網羅の結果から、通っていない分岐を見つけ、統合とシステムの観点に漏れがないかを確かめる。
- コードを読んで分かった内部の判定（上限値の判定など）を、因子や水準に加える。

期待結果は仕様から書き、コードから書かない。
コードから書くと、不具合のある動作を正しい結果として扱ってしまうためである。
仕様から期待結果を書けないときは、推測で埋めずに質問として示す。

## 探索的テスト

探索的テストは、手順を決めたケースを補うものとして使う。

| 方法 | 使う場面 |
| --- | --- |
| 手順を決めたケース | 期待結果を仕様から書ける。毎回同じ手順で確かめる |
| 探索的テスト | 仕様が決まっていない、新しい機能である、リスクが高いが観点を出しきれない |

段階2で探索的テストに回すとした観点には、ケースの代わりにチャーターを出す。
チャーターには、対象、探す観点、時間の上限、記録することを書く。
チャーターには期待結果がないため、[良いテストケースの基準](#良いテストケースの基準)のうち「手順と期待結果が対になる」は当てはめない。

## 良いテストケースの基準

スキルの出力は、次の基準を満たす。
各基準の根拠は[根拠](#根拠)に示す。

| 基準 | 満たす条件 |
| --- | --- |
| 目的が一つ | タイトルが、確かめる内容を表す文になっている。確かめる内容が二つあるケースは分ける |
| 手順と期待結果が対になる | 確かめる手順には、観察できる期待結果がある。「正常に動く」「問題ない」のように、何を見れば判定できるか分からない期待結果を使わない |
| 手順に重複と抜けがない | 確かめない準備の操作は事前条件へ移し、手順には目的に必要な操作だけを残す |
| 実施に必要な情報がそろう | 事前条件に、使うデータ、画面、状態を具体的に書く。初めて実施する人が、ほかの資料を読まずに実施できる |
| 何度実施しても同じ結果になる | ほかのケースの実施結果に依存しない。事後処理で、変えたデータや設定を元に戻す |
| 仕様との対応をたどれる | 観点ごとに、根拠の仕様と、確かめたケースを両方向にたどれる |
| 不具合を見つけられる | 仕様の網羅に加えて、不具合が起きやすい箇所を確かめるケースがある |

ケースの粒度は、テストの目的で選ぶ。
新しい機能や不具合を探すテストでは、上の基準どおりに分ける。
変更の少ない機能を最終確認するテストでは、同じ事前条件を使う複数の確認を、一件にまとめてよい。

## 手順

スキルは、次の順序でケースを導く。
各段階の出力を次の段階の入力にし、段階を飛ばさない。

| 段階 | すること | 出力 |
| --- | --- | --- |
| 1. 目的とリスクの確認 | [テストレベル](#テストレベル)を決め、そのレベルで確かめる仕様から、確かめる内容と、不具合が起きやすい箇所を挙げる。過去のバグ報告も材料にする | テストレベル、テストの目的、リスクの一覧 |
| 2. 観点の洗い出し | [観点の切り口](#観点の切り口)で、確かめる観点を木の形に整理する。観点ごとに、手順を決めたケースにするか、[探索的テスト](#探索的テスト)に回すかを決める | 観点の木。対象外にした観点と理由 |
| 3. 人の確認 | テスト担当者が、観点の抜けと優先度を確認する | 確認済みの観点の木 |
| 4. 因子と水準の決定 | 観点ごとに、結果を変える条件（因子）と、その値（水準）を挙げる。水準は有効な値、無効な値、境界値に分ける。成り立たない組み合わせを制約として書く | 因子と水準の表、制約 |
| 5. 組み合わせの決定 | [組み合わせの規則](#組み合わせの規則)で、実施する組み合わせを決める | 組み合わせの表 |
| 6. ケースの作成 | 組み合わせの表の各行を、[出力の形式](#出力の形式)でケースにする。探索的テストに回した観点はチャーターにする | テストケースの案、チャーター |
| 7. 点検 | [良いテストケースの基準](#良いテストケースの基準)と、観点・組み合わせの網羅を確かめる | 観点とケースの対応表、点検で直した箇所 |

スキルは段階3で止まり、テスト担当者の回答を待つ。
観点の抜けは、後の段階で補えないためである。
仕様から判断できない因子や水準は、推測で埋めずに質問として示す。

### 観点の切り口

観点は、次の切り口で洗い出す。
対象に当てはまらない切り口は、理由を付けて対象外にする。

- 機能：仕様に書かれた動作
- データ：有効な値、無効な値、境界値、空、上限
- 状態：状態ごとの動作と、禁止された遷移を含む状態の遷移
- 時間とタイミング：期限、時刻、操作の順序、連続した操作
- 量：件数、長さ、大きさ
- 権限と利用者：操作できる人とできない人
- 中断と再開：取消し、再読込み、通信の失敗、保存前の画面移動
- 環境：OS、ブラウザー、対象モデルなど、テスト計画の実施条件

### 組み合わせの規則

全組み合わせを実施せず、因子の性質に応じて組み合わせを絞る。

| 因子の性質 | 実施する組み合わせ |
| --- | --- |
| ほかの因子と影響し合わない | 各水準を一回以上 |
| ほかの因子と影響し合う可能性がある | 2因子間のすべての水準の組（ペアワイズ） |
| 段階1でリスクが高いとした因子 | 3因子以上のすべての水準の組 |
| 数値や長さの範囲がある | 境界値と、その前後の値 |
| 状態が遷移する | すべての遷移と、禁止された遷移 |
| 無効な値 | 組み合わせの表とは別に、一件に一つだけ含める |

無効な値を一件に一つだけにするのは、失敗したときに原因の水準を特定できるようにするためである。
制約に当たる組み合わせは、表から除く。

## 出力の形式

出力の項目は、[テストケースの項目](test-management.md#項目)に合わせる。

| テストケースの項目 | スキルの出力 |
| --- | --- |
| タイトル | 確かめる内容を表す文 |
| 目的 | 対応する観点と、確かめる理由 |
| 事前条件 | 使うデータ、画面、状態 |
| 手順 | 番号付きの操作 |
| 期待結果 | 手順と同じ番号を付けた、観察できる結果 |
| 事後処理 | 元に戻す操作 |
| カテゴリ | 観点の木の、最上位の観点 |
| 優先度 | 段階1のリスクから決めた High、Medium、Low |
| テスト種別 | Manual。チャーターは Exploratory |
| 状態 | Draft |
| 関連する仕様 | 根拠の仕様やIssueへの参照 |

ツールでは手順と期待結果を別の項目に保存するため、同じ番号で対応させる。
出力するケースの状態はDraftとし、テスト担当者が確認してからActiveにする。

ケースとは別に、観点とケースの対応表を出力する。
対応表では、各観点・各水準・組み合わせの表の各行が、どのケースにあるかを示す。
