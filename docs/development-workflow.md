# 開発手順と実施記録

作業担当と確認する人が、変更をどの手順で進め、何を確かめたかをIssue・PRから追うための手順である。
機能追加、不具合修正、文書変更、試作に適用する。
担当は工程ごとに証拠を残し、提出前に実施記録と成果を照合する。

## 工程

| 工程 | 作業担当が行うこと | 次へ進むための根拠 |
| --- | --- | --- |
| 1. 着手 | 対応Issue、目的・完了条件、今回の範囲、前提、指示で許可された操作を確認する。Projectと作業場所を確認する | Issue・Projectへの参照、今回扱う完了条件、開始指示と操作範囲、worktreeと変更前の状態 |
| 2. 設計 | 要件と既存仕様を照合し、今回満たす条件と確かめ方を決める。UIは観察から試作までの手順を行う | 仕様・検討資料、完了条件と検証方法の対応。判断が必要な変更は採用範囲と判断の記録 |
| 3. 変更 | 決めた範囲を実装・文書化し、影響する仕様も更新する | PR差分とcommit、完了条件ごとの成果。範囲外や後続に残す内容 |
| 4. 検証・レビュー | 完了条件を確認し、該当するテストとレビューを行う。指摘を修正して再確認する | 対象版、実施者・日時、コマンドまたは操作手順、結果、ログ・画像・レビュー記録 |
| 5. 提出 | 下記の提出前照合を行い、判断対象と残る範囲を示す | 今回求める判断、対象版、工程と完了条件の証拠、未確認事項。Ready化の条件を確認した記録 |
| 6. 受入 | 対象版への回答を確認し、許可された取り込みを行う。Issueの受入結果を更新する | 承認した範囲と回答の参照、取り込み結果、利用者による受入結果。未完了の条件は残す |

着手・worktree・Project・Issue・PR・リリースの具体的な規則は[AGENTS.md](../AGENTS.md)を正本とする。
検証コマンドは[開発と検証](development.md#検証手順)、UIの点検は[UI/UXレビュー](ui-ux-review.md)、文書の点検は[文章とGit](../AGENTS.md#文章とgit)から参照する。
文書のみに変わった場合も、関連文書との整合、参照先、表示を確認する。
不要な検証は対象外の理由を残し、未実施を成功として扱わない。

各工程は、その工程の成果ができた時点で記録する。
後から記録を補う場合は「事後確認」とし、当時の証拠を確認できない実施内容や順序を、手順どおりだったと記さない。
仕様や範囲が変わった場合は設計へ、検証後に変更した場合は影響する検証へ戻る。
前提がそろった独立の作業は並行して進め、工程を管理するためだけにIssueを分割しない。

## 記録の置き場所

| 情報 | 正本 |
| --- | --- |
| 目的・完了条件・受入結果 | 作業Issue |
| 担当・状態・Iteration・Estimate・優先度 | GitHub Project |
| 現在の工程、停止理由・再開条件、次の行動と担当 | Issue本文の「進行」 |
| 今回の変更範囲、工程の実施記録、検証結果、判断対象の版 | PRと、そこから参照する証拠 |

PR作成前はIssueの「進行」から成果を参照し、PR作成後は実施記録をPRへまとめる。
Issueには次の行動とPRへの参照を残し、工程表や検証結果を写さない。
別文書にレビューや画像がある場合、PRはその対象版へのリンクを持つ。
部分PRの工程とIssue全体の状態を混ぜず、ReadyやマージだけでIssueを受入完了にしない。

## PRに残す証拠

[PRの書式](../.github/pull_request_template.md)を使い、完了条件と工程の二つの観点で証拠を示す。
前者では要求を満たす範囲、後者では手順を実施した事実を確認する。
同じ証拠は再掲せずリンクを使い、工程数やチェック済み件数を進捗率にしない。

- 対象版はcommitで示し、検証した版と提出版が違う場合は差分と再確認の範囲を記す。
- 実行記録には実施者・日時・条件・結果を付ける。
  コマンドは再実行できる形で示し、操作確認は対象画面と手順を示す。
- ログや画像は必要な箇所へ絞り、公開できる証拠をPRから開ける場所に置く。
  ローカルのパスや「確認済み」という記述だけでは、第三者が実施を確かめられる証拠として扱わない。
- レビューには対象版と確認者、指摘・修正・再確認を残す。
  自己点検と別担当によるレビューを区別し、別エージェントへの依頼条件はAGENTS.mdに従う。
- 未確認・対象外には理由と影響を添える。
  判断を求める段階と範囲を明示し、試作の点検を製品全体の受入に読み替えない。

## 提出前の照合

作業担当は提出前に次を順に確かめ、結果をPRの「提出」行に残す。

1. 今回扱うIssueの完了条件から、変更箇所と検証結果をたどれる。
2. 工程1〜4の根拠を開け、対象版・実施内容・結果が記録と一致する。
   チェック印やテスト件数だけを根拠にしない。
3. 未修正の問題、必要な確認の不足、古い版だけの検証を残していない。
   対象外の理由が今回の範囲と合い、必要な条件を省略していない。
4. 判断してほしい範囲と残る作業を分け、[Ready化の規則](../AGENTS.md#issueとgithub-project)を満たす。

不足があればDraftを維持し、Issueの「進行」に不足・再開条件・次の行動と担当を記す。
修正後は該当工程の証拠と提出前照合を更新する。
受入工程は人間の回答前に確認済みとせず、提出できる範囲だけをReadyにする。

確認する人は、PRの完了条件の表から成果を、工程表から手順の証拠を開き、必要な項目を照合できる。
この書式は実施の確認を支えるものであり、記入だけで品質を保証したり、自動でReady化を禁止したりするものではない。
