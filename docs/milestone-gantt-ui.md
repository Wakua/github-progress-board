## 行動の整理

B1・B2・G1・F1の観察記録と画像を再確認し、既存試作の日→週→月→日と結合確認の詳細を操作した。
色の凡例・依存矢印・表示切替・文字量削減は既存版にある。
前提名から別作業へ続けて移る操作、担当重複、不足の原因からの移動は今回の試作へ加えた。
以下の表示候補は、利用者の行動の仮説を検証するためのものであり、採用済みの画面仕様ではない。

| 判断したいこと | 見る場所 → 判断 → 次の操作 | 根拠と限界 |
| --- | --- | --- |
| 期日に間に合うか | 見込み・期日差・破線の期日 → 超過か余裕か → リリース名で基準日と取得時点を確認 | B2と計算要件。実利用者の理解は未確認 |
| どの作業を優先するか | ◆の作業と依存矢印 → 完了を左右する連なり → 作業名から前提・後続を選ぶ | B1・B2・G1。詳細内の連続移動は今回の試作で操作確認 |
| 誰の計画を見直すか | 「担当調整」の件数 → 同時に重なる作業と期間 → 対象作業の詳細を開く | B3では重複警告を観察できていない。計算要件を根拠にした候補 |
| 何が不足しているか | 「情報不足」の件数 → 対象と不足項目 → 原因作業から後続へ移る | 他社での操作観察は未確認。計算結果の診断を使う候補 |
| どの範囲まで確認できるか | 「重複未確認」→ 外部Project・担当不明・日程未算出 → 対象作業を開く | 警告なしを重複なしと誤解しないための候補 |
| 時間軸を変えて追いたい | 表示期間と選択中の単位 → 必要な細かさ → 日・週・月を選ぶ | F1を参照。計算結果を再計算せず保持 |


## 開始条件の表示候補

[既存の作業分類](specification.md#githubから表示する計画)と、[日程に使う前提](milestone-gantt.md#計算する作業と依存関係)が異なる場合を検討する。
対象は、Closedの親を前提に持ち、その配下には未完了の作業があるケースである。

| 候補 | 表示と操作 | 利点 | 懸念 |
| --- | --- | --- | --- |
| A：一覧に開始条件を添える | 既存の分類と短い理由を表示し、選ぶと前提の内訳を開く | 日程上もすぐ始められるとの誤解を避けやすい | 該当する行が多いと情報量が増える |
| B：違いを詳細にまとめる | 一覧は作業と日程を中心にし、詳細に既存分類と開始条件を置く | 一覧に載せる情報を抑えられる | 詳細を開くまで違いに気づかないおそれがある |

現在の試作はBを基にする。
採用の判断には、利用者が開始条件を誤解せず説明できるかの確認が残る。

他の作業とポートが重なる場合は、起動前に環境変数 `PORT` を指定する。

### 実装へ渡す契約の候補

採用の判断対象は、警告から詳細へ進む入口と、詳細内で前提・後続を追って戻る流れである。
計算式、出典、保存形式は変更しない。

| 入力・結果 | 表示と操作の候補 |
| --- | --- |
| `milestones` | 開いたMilestoneを表示し、閉じたものを除く。作業未登録と全作業完了を分け、将来の完了日を推定しない |
| `finish`、`dueDate`、`dueDifference` | 見込み、期日、平日の日数による差を一覧へ置く。期日未設定と計算不能を区別する |
| `earliestStart`、`earliestFinish`、`durationDisplay` | 暦上の位置に棒を置く。0日は点、短い棒の日数は作業名の側、正確な開始・完了は詳細に置く。日内の端数を時刻へ換算しない |
| `criticalTaskKeys`、`criticalEdgeIds` | ◆、太い枠、依存線で識別する。複数経路も保持し、色だけに意味を持たせない |
| `relations`、`edges.evidence`、`hierarchy` | 登録された親と配下を詳細で表示する。親がClosedでも待つ子を確認でき、子・前提・後続を選ぶとその詳細へ移る |
| `overlaps` | 見込みの近くに「担当調整」の入口を置き、担当・対象作業・重複期間を表示する。日程を自動変更しない |
| `diagnosticIds`、`cycles` | 理由と原因作業への入口を表示する。不足する作業と後続の棒を出さず、既知の日程と詳細の依存関係は残す |
| `overlapUnchecked`、`iterationOverflow` | 重複を確認できない理由、Iterationを超える日数と終了日を詳細で確認する |
| 既存分類、見積、作業進捗率、担当 | サンプルの表示情報を詳細へ渡す。100%でも未完了の状態を表示し、計算で既存分類を書き換えない |
| 詳細の移動 | 「戻る」で直前の詳細へ移り、「閉じる」またはEscapeで一覧へ戻る。入口のフォーカスと横スクロール位置を保持する |

日表示は月曜から最短1週間、週表示は月曜から最短4週間、月表示は月初から最短3か月とする。
作業または期日が範囲外になる場合は、日・週は週単位、月は月単位で期間を広げる。
月の幅は暦日数に比例し、日表示の土日には曜日と背景を付ける。
この期間の選び方は試作条件であり、製品の既定値は未決定である。

## 操作検証

2026-10-31にCodexがChromeで架空のサンプルを操作した。
通常幅800×700、狭い幅320×720、幅800で文字200%を確認した。
これは担当者による実操作であり、実利用者の行動観察ではない。
対象版と必須の問いI1〜O2の判定は、この変更のPR本文「UIレビュー」を正本とする。
[操作で取得した表示と検証記録](verification/127-gantt-ui.json)を参照できる。
固定3作業の旧版のレビューは[PR #130](https://github.com/Wakua/github-progress-board/pull/130)に残る。

| 条件・操作 | 確認した結果 |
| --- | --- |
| 基本：結合確認 → 実装B → 後続の結合確認 → 戻る → Escape | 前提・後続を続けて追い、元の結合確認の行へフォーカスが戻った。Closed親の子2件と既存分類を確認した |
| 担当の重複 → 担当調整1件 → 実装A | 担当A、11/2開始〜11/3終了、対象2作業を確認し、作業の詳細へ移った。日程の変更はなかった |
| 情報不足 → 理由 → 実装B → 結合確認 | 作業進捗率の未入力を確認した。実装Aの日程は残り、不足する実装Bと後続の日程・全体見込み・クリティカルは未算出になった |
| 循環 → 理由 | 循環する実装A・Bを確認した。独立した作業の日程は残った |
| 0日と端数 → 実装Aの詳細 | 0日の点、100%・未完了、0.5日2件、0.01日未満の超過を区別した |
| 金曜・年境界・土日の期日 → 日・週・月 | 金曜1/1から月曜1/4までの2日、期日1/3、見込み1/5、1.5日超過を保持した。月幅は12月31日・1月31日・2月28日に対応した |
| 期日未設定・複数の経路 → 日・週・月 | 見込みと2本のクリティカルな接続を保持し、期日を未設定と表示した |
| 中間の親・外部の前提 → 重複未確認 → 対象 → 結合確認 | 対象Project外と担当不明を区別した。親→中間の親→最下位2作業を表示した |

日→週→月→日の切替では、棒の説明にある開始・完了・日数、依存関係とクリティカルの識別、見込みと期日差が変わらないことを照合した。
切替で保持する進捗率・余裕は、同じ計算結果を参照する構造とテストでも確認する。

### 点検で直した箇所

- 詳細の親配下と前提一覧で同じ作業が重複したため、親配下から直接選べるようにした。
- 未算出を行内に重ねて表示したため、日程欄へ一度だけ置いた。
- 拡大表示で期日のラベルと日付が重なったため、期日は破線と凡例で示した。
- 未入力・循環の内部コードは画面へ出さず、項目と理由を日本語で示した。
- 0日の直後へ向かう依存線が固定した作業名列に隠れたため、棒の上辺へ接続し、日・週・月で再確認した。

### 利用者に確認する課題

候補Bを基にした試作について、操作場所や正解を先に伝えず、次を依頼する。
観察した行動と説明後の結果は分けて記録する。

1. 結合確認をいつ始められるか、判断の根拠を説明する。
2. 実装Bが遅れた場合、何へ影響するか調べる。
3. 担当の重複サンプルで、見直す必要のある作業と期間を調べる。
4. 情報不足サンプルで、日程を出すために必要な情報を調べる。

## 未確認と判断対象

画面案の採用、実利用者の理解、GitHubの実データ、本番への組込みは未確認である。
新しい入口を一覧上部の短い件数にまとめる案と、該当する行にも理由を添える案の比較を利用者へ示す。
前者は一覧の文字量を抑えられる一方、対象を知るまで1操作かかる。
後者は対象をすぐ見つけられる一方、行の情報量が増える。
今回の試作は前者であり、利用者による採用判断を置き換えない。

ブラウザのズーム操作、スクリーンリーダーの読み上げ、タッチ実機、多数の作業での探索は未確認である。
文字200%の表示確認を、これらの検証やWCAGへの適合とは扱わない。
GitHubリンクは対象URLを別タブで開くことを確認したが、架空のIssueのため404となる。
実在するIssueの内容確認は本番への組込み時に行う。
取得と書込みの状態・保存形式は各担当の契約に従い、本試作で新たに定義しない。
