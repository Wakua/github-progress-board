# テストケースの登録・編集

ローカル版を使うテスト担当者と開発担当者向けに、ケースの保存、再読込み、競合時の操作を示す。
計画の作成、結果の記録、Bug連携は後続の対象であり、この画面には含めない。

## 起動と操作

[READMEの起動手順](../README.md#起動と検証)でサーバーを起動し、進捗管理の「テスト管理」を開く。
直接開く場合は `/testing/` を使う。
クラウド版には入口と保存APIを含めない。

1. 「＋ ケース」で入力欄を開く。
   IDはサーバーが採番し、状態はDraftで始まる。
2. 必須項目を入力し、「保存」を押す。
   カテゴリは既存候補から選ぶか、新しい名前を入力する。
3. 一覧のカテゴリ・状態で絞り、ケースを選んで編集する。
   Deprecatedにしても記録は残り、状態の絞込みで開ける。

ケース項目と必須条件は[テスト管理の仕様](test-management.md#テストケース)を正本とする。
一覧を閉じると編集欄が広がり、再び開いてもケース、絞込み、一覧位置、未保存の入力を保持する。
760px以下では一覧を編集欄の上に開き、同じケースの再選択も含めて、選択後は一覧を閉じて編集見出しへフォーカスを移す。
再起動後の開閉設定は保存しない。
任意項目は「補足」から開く。

## 保存と復旧

[別DBの採用記録](https://github.com/Wakua/github-progress-board/issues/170#issuecomment-6875064145)に従い、バグ管理と別のSQLiteファイルを使う。
既定の保存先は起動フォルダーの `.test-management-data/tests.sqlite` である。
`TEST_MANAGEMENT_DATA_DIR` で保存フォルダーを変更できるが、公開する `dist` の中には置かない。
進捗管理のブラウザー保存と、テストケースのDBは別々に保持する。
バックアップはサーバーを終了してから保存フォルダー全体をコピーする。

保存成功後のケースと状態は、ページ再読込み・サーバー再起動後も保持する。
未保存入力は画面内だけに保持し、ブラウザーやPCの終了からの復旧は保証しない。
別ケースへの移動とキャンセルでは、入力を破棄するか確認する。
ページを離れるときはブラウザーの未保存確認を使う。

- 保存失敗：入力を残し、成功とは表示しない。
  保存先が復旧した後に、同じ画面で「保存」を再試行する。
- 競合：入力を残したまま「最新内容を見る」で保存済み内容と比べる。
  必要な入力を控え、キャンセルで未保存入力を破棄し、ページを再読込みして最新のケースを編集する。
  競合の自動統合や強制上書きは行わない。
- 一覧の取得失敗：「再取得」で読み直す。
  DBの初期化失敗でも進捗管理の画面は起動する。

## 保存の内部契約

`dist/testing/repository.mjs` が同一オリジンのHTTP APIへ接続する。
`case-editor.mjs` は画面の状態、`server/test-store.mjs` は採番・永続化を担当する。

| 操作 | API | 保存側の動作 |
| --- | --- | --- |
| 一覧 | `GET /api/testing/cases` | ケースと保存済みカテゴリ名を返す |
| 新規入力 | `POST /api/testing/case-ids` | IDを予約する。未保存の予約は一覧に入らず、欠番は再使用しない |
| 保存 | `PUT /api/testing/cases` | `values`、取得時の`revision`、`requestId`を照合して保存する |

ローカルサーバーはlocalhost/127.0.0.1のHostを照合し、APIには専用ヘッダー、書込みには同一Originを要求する。
インターネットへ公開するための認証機能ではない。
ケースの更新番号が一致しなければ409と最新内容を返す。
同じ内容の再試行には同じ受付キーを使い、同じキーの違う内容は拒否する。
ケース更新と受付記録は一つのSQLiteトランザクションで確定し、受付記録は再起動後も保持する。
受付記録の自動削除は行わない。

DBはWAL・同期FULL・外部キー有効で開き、書込み待ちは3秒とする。
未対応のDB版や、版番号のない既存テーブルを検出したら書き換えずに停止する。
APIはJSONを256KiB以内に制限する。
タイトルは500文字、カテゴリは120文字、関連仕様は2,000文字、長文欄は各20,000文字までとし、不正な値や未知の項目を拒否する。

## 結果の保護と後続の境界

ケース編集は `case_ids`、`cases`、`case_receipts` だけを扱い、結果やバグ管理のDBを更新しない。
検証では独立した結果コピーを実SQLite内に置き、ケースを更新してもコピーが変わらないことを確認する。
これは結果記録機能の実装ではなく、ケース更新側の書込み境界の確認である。
初回結果時の内容コピーと、計画・実施条件ごとの保持は、[保存の仕様](test-management.md#保存)に従う後続の実装で確認する。

将来のBug連携では、別DB間を一つのトランザクションにできないため、固定受付キーと再送・照合が必要になる。
このPRではBug受付、再送処理、GitHub書込みを追加しない。

## 検証用の起動

```sh
node --test tests/test-case-editor.test.mjs tests/test-case-store.test.mjs tests/test-case-api.test.mjs
node tests/test-case-screens-server.mjs <Git管理外の専用フォルダー> 4497
```

後者は専用フォルダーに架空のケースを保存し、通常の製品画面と実SQLiteを接続する。
`http://127.0.0.1:4497/testing/` で、保存・再読込み・同時編集を確認できる。
既存のテスト用メモリ接続は `tests/support/test-case-fixture.mjs` に分離し、製品の保存先には使わない。
