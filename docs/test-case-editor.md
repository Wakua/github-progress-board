# ケース編集画面の接続と検証

#170を実装する担当者向けに、画面モジュールの接続範囲と確認方法を示す。
この変更は保存先を接続する前の部分実装であり、製品の登録機能としては提供しない。
実データの保存・再起動後の保持・結果の内容コピーは対象外である。

## 採用した操作

[本人のC案採用と着手範囲](https://github.com/Wakua/github-progress-board/issues/170#issuecomment-6872130247)を根拠とする。
一覧を閉じると編集欄が広がり、再び開いてもケース、絞込み、一覧位置、未保存の入力を保持する。
760px以下では一覧を編集欄の上に開き、同じケースの再選択も含めて、選択後は一覧を閉じて編集見出しへフォーカスを移す。
再起動後の開閉設定は保存しない。

一覧にはID・タイトル・状態を置き、編集欄には必須項目とカテゴリを置く。
目的・事前条件などの任意項目は「補足」から開く。
別のケースへ移る操作とキャンセルでは、未保存の入力を破棄するか確認する。

## 接続範囲

`dist/testing/case-view.mjs`の`mountCaseEditor`に、呼出側が保存接続口を渡す。
`case-editor.mjs`は画面の入力値と選択状態を管理する。
以下は内部接続口であり、HTTP APIやDBの物理モデルではない。

| 操作 | 接続口が返す内容 | 画面の責務 |
| --- | --- | --- |
| `load()` | ケース配列とカテゴリ名の配列 | 読込み失敗を表示し、再取得できるようにする |
| `newCase()` | IDを持つ未保存ケース | Draftの入力欄を開く。採番・予約方式は保存側の設計で決める |
| `save({values,revision,requestId})` | 保存したケース | 必須検証、二重操作防止、入力保持、保存応答の照合を行う |

値には#170のケース項目だけを渡す。
同じ内容の保存を再試行するときは同じ受付キーを使い、入力が変わったら新しいキーを使う。
接続口が競合と最新内容を返した場合、画面は入力を保持して最新内容を別表示し、無条件で上書きしない。
競合の統合・上書き操作は今回含めない。
実接続側の認証、採番、更新番号、受付キーの有効期間と永続化は未実装である。

通常のナビゲーションやローカルサーバーには接続していない。
クラウドのビルドには含めず、保存接続の判断後にローカルモードへ組み込む。
模擬接続は`tests/support/test-case-fixture.mjs`だけに置き、製品コードには仮保存を持たせない。

## 確認する方法

```sh
node --test tests/test-case-editor.test.mjs
node tests/test-case-review-server.mjs 4495
```

ブラウザーで `http://127.0.0.1:4495/` を開く。
ページ上部の表示どおり、架空データはメモリ内だけに保存し、再読込みで初期化する。
「次の保存」は失敗・競合・応答消失を返す検証用の操作である。
SQLite障害や実際の同時編集を再現したものではない。

1. TC-101の期待結果を変え、一覧を閉じて開く。
   ケース・入力・絞込み・一覧位置が残ることを確認する。
2. 別ケースを選び、「編集を続ける」と「破棄して移動」の両方を試す。
3. ケースを追加し、空の必須欄で保存を試す。
   タイトルへフォーカスが移り、入力後は一覧に追加されることを確認する。
4. 保存失敗と競合を選び、入力が消えず、成功と表示されないことを確認する。
5. 幅390pxで一覧を開き、同じケースを選び直す。
   一覧が閉じ、編集中の入力が残ることを確認する。
6. Enter・Spaceで一覧を開閉し、閉じた一覧にTabが入らないことを確認する。

## 保存境界の未決定事項

SQLite、Nodeローカルモード、初回結果時の内容コピーは採用済みである。
DBファイルをバグ管理と分けるかは未決定で、C案の採用には含まれない。

| 案 | 利点 | 影響・残る設計 |
| --- | --- | --- |
| 別のSQLiteファイル（推奨） | 移行・復旧を分離し、既存バグ管理への変更を抑える | 将来のBug連携では二つのDBを一度に確定できないため、固定受付キーと再送・照合が必要 |
| 既存DB内の別テーブル | 結果とローカルBug受付を同じトランザクションで確定できる | DB版番号・移行・書込み待ちを共有し、移行失敗が既存バグ管理にも影響する |

根拠はmain `9b7dc5d`の`server/bug-store.mjs`である。
既存のDB移行、更新番号による競合検出、受付キーによる重複防止と責務を照合した。
どちらの案でもGitHub側の書込みまでを同じトランザクションにはできない。

採用後は保存アダプターとローカルモードへの組込みを実装し、SQLiteの保持・障害・並行更新を検証する。
既存結果の内容を変えない要件は、画面が受け取った結果を直接変更しないことだけを今回確認している。
実DBでの初回内容コピーと旧結果保持は後続の接続検証として残る。
