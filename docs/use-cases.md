Issue #26 の記録。このツールが助ける場面と、そのために表示するものを一つにまとめる。

根拠は、[AGENTS.md](../AGENTS.md) の運用、[README](../README.md) の仕様、以前のIssue、2026-10-05 のWakuaの回答（次の3つの場面のすべてに困っている）である。実利用者の行動は観察していない。場面はAIが資料から組み立てた推測であり、回答で確認した範囲を「確認」の列に示す。

## 前提

- 作業は、人（Wakua）と、AI（Claude・Codex）が並行して行う。AIが作業を進めるほど、人の判断と承認が必要な場面が増える。
- 人の主な作業は、判断と承認である。作業の担当は、GitHub Project の「担当」（Wakua・Claude・Codex）で示す。
- リリースは、2イテレーション（2週間）ごとに Milestone で区切る。期日後にWakuaが main を確認し、フィードバックする。

## 場面2：リリースの期日が近い

| 項目 | 内容 |
| --- | --- |
| 状況 | Milestone の期日（例：2026-11-01）までに、予定した作業が収まるかを知りたい |
| 今の困りごと | GitHub の Milestone は、閉じた件数の割合と期日だけを出す。収まらない作業は、見積とイテレーションを自分で突き合わせて探す |
| 知りたいこと | 期日までの残りイテレーション数と残りの Estimate。期日より後に割り当てた作業、未割当、見積なし、期限切れの作業。遅れると全体が遅れる前提の流れ |
| 判断 | 割当を変えるか、範囲を減らすか（間に合うかの判定は人が行い、ツールは完了予定日を出さない） |
| 次の操作 | 作業を開き、GitHub 上で Project の Iteration を変える |
| 対応する画面 | ② イテレーションのリリース（期日・終了率・残りの Estimate は実装済み）、④ リリース（未実装） |
| 確認 | Wakuaの回答で確認した |

| 項目 | 内容 |

| 状況 | AIに頼める作業が増えるほど、Wakuaの承認と確認が増える。承認待ちが多すぎると、判断が遅れる |
