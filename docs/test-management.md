# テスト管理の仕様

対象読者は、テスト管理機能を設計・実装する人。
対象範囲は、初期リリースで提供するテストケース・テスト計画・テスト結果・Bug連携・集計の仕様。
読むと、何を保存し、何を画面で扱い、何を初期リリースに含めないかが分かる。

範囲外は、画面の配置と見た目（UI設計の手順に従って別に決める）、保存先のデータ構造、AIによるテストケース生成。

## 目的

テストについて、次を一貫して管理する。

- 再利用できるテストケースの定義
- バージョン、OS、対象モデルを指定したテスト計画
- テストケースごとの実施結果
- 実施状況と合格・不合格の集計
- 不合格の結果からのBug Issue登録
- Bug修正後の再テスト
- 過去の実施結果の参照

テストケースの内容と、特定バージョンに対する実施結果は、別の情報として管理する。

## 情報の構造

```
テストケース
  ↓ 選択
テスト計画
  ↓ 実施
テスト結果
  ↓ 必要に応じて
Bug Issue
  ↓ 修正後
再テスト結果
```

| 情報 | 内容 |
| --- | --- |
| テストケース | 何を、どの手順で確認するかの定義。複数のテスト計画から再利用する |
| テスト計画 | 特定のバージョン、OS、対象モデルに対して実施するテストケースの集合 |
| テスト結果 | テスト計画内の各テストケースの実施結果。結果を変更しても、テストケースの定義は変えない |
| Bug Issue | テストで見つかった問題。作成元のテスト結果と相互に参照できる |

同じテストケースを異なるバージョンや環境で実施する場合は、別のテスト結果を作る。

## テストケース

### 項目

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| ID | ○ | テストケースを一意に識別するID |
| タイトル | ○ | 確認内容を端的に示す名称 |
| 目的 | | このテストで確認する内容 |
| 事前条件 | | 実施前に満たす条件 |
| 手順 | ○ | 実施する操作 |
| 期待結果 | ○ | 正常な場合に得られる結果 |
| 事後処理 | | テスト後に必要な復旧・終了操作 |
| カテゴリ | | 機能、画面、コンポーネントなどの分類 |
| 優先度 | | High、Medium、Low |
| テスト種別 | | Manual、Automated、Exploratory など |
| 状態 | ○ | Active、Draft、Deprecated |
| 関連する仕様 | | GitHub Issue、仕様書、要件への参照 |
| 備考 | | 補足 |

### 状態

| 状態 | 意味 |
| --- | --- |
| Draft | 作成中。通常のテスト計画には追加しない |
| Active | 実施できる |
| Deprecated | 廃止済み。履歴のために保持する |

### 変更

テストケースを変更しても、過去のテスト結果に記録された内容を、変更後の内容で上書きしない。

## テスト計画

### 項目

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| ID | ○ | テスト計画を一意に識別するID |
| 名前 | ○ | 計画の名称 |
| 目的 | | テスト対象と実施目的 |
| 対象バージョン | ○ | テスト対象のソフトウェアのバージョン |
| 対象ビルド | | 実際に使うビルド番号 |
| OS | | Windows、macOS など |
| OSバージョン | | OSの具体的なバージョン |
| 対象モデル | | 対象の製品・機種・モデル |
| 担当者 | | テスト計画全体の担当者 |
| 開始日 | | テスト開始日 |
| 完了日 | | テスト完了日 |
| 状態 | ○ | Draft、In Progress、Completed、Archived |
| テストケース | ○ | この計画で実施するケース |
| 関連Issue | | リリース、Feature、Requirement などへの参照 |

環境によって結果が変わる場合は、OSや対象モデルをテスト計画に明示する。

### 状態

| 状態 | 意味 |
| --- | --- |
| Draft | ケースの選択と条件の設定中 |
| In Progress | テストを実施中 |
| Completed | 必要なテストが完了している |
| Archived | 過去の記録として保管している |

### テストケースの追加

テスト計画には、Active状態のテストケースを追加できる。
追加方法は次の4つ。

- テストケース一覧から個別に追加する
- 複数のテストケースを一括で追加する
- カテゴリで絞り込んで追加する
- 過去のテスト計画から複製する

追加した時点では、各テストケースの結果を Not Run にする。

## テスト結果

### 状態

| 状態 | 意味 |
| --- | --- |
| Not Run | 未実施 |
| Passed | 期待結果を満たした |
| Failed | 期待結果を満たさなかった |
| Blocked | 外部要因により実施または判定できなかった |
| Skipped | 本来は対象だが、今回は実施しなかった |
| Not Applicable | 今回の環境や対象モデルでは対象外 |
| Retest Required | 修正などにより再テストが必要 |

SkippedとNot Applicableは区別する。

### 項目

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| テスト計画 | ○ | 所属するテスト計画 |
| テストケース | ○ | 実施したテストケース |
| 結果 | ○ | Passed、Failed など |
| 実施者 | ○ | 結果を記録したユーザー |
| 実施日時 | ○ | 結果を記録した日時 |
| 実際の結果 | Failed のとき必須 | 実際に起きた動作 |
| コメント | | 補足 |
| 添付ファイル | | スクリーンショット、ログなど |
| 関連Bug | | この結果から作成・関連付けしたBug |
| 再テスト元 | | 再テストのとき、前回の結果 |
| 対象ビルド | | 実際にテストしたビルド |
| 実施環境 | | 実施時のOS、モデルなど |

### Passed の記録

Passed は、最小の操作で記録できるようにする。
操作は、Passed を選び、保存し、次の未実施ケースを表示する、の順。
Passed では、コメントも添付ファイルも求めない。

### Failed の記録

Failed を選んだときは、次を入力できる。

- 実際の結果（必須）
- コメント
- スクリーンショット、ログ
- 関連する既存Bug
- 新しいBugの作成

Bug Issueの作成は必須にしない。
既知の問題、仕様の確認中、重複などの理由で、作らない場合があるため。

## テスト実施画面

### 表示

画面には、次を表示する。

- テストケース一覧：名称、現在の結果、担当者、関連Bugの有無、再テストの要否
- 選択中のテストケース：タイトル、目的、事前条件、手順、期待結果、関連する仕様、過去の結果
- 結果入力：結果の選択、実際の結果、コメント、添付ファイル、Bugの作成・関連付け

結果を保存したあとは、次の未実施ケースへ移動できる。

### キーボード操作

結果を繰り返し入力するため、次のキー操作を提供する。

| 操作 | キー |
| --- | --- |
| Passed | P |
| Failed | F |
| Blocked | B |
| 次のケース | ↓ または J |
| 前のケース | ↑ または K |
| 保存 | Ctrl+Enter / ⌘+Enter |

入力欄に文字を入力しているときは、結果を変えるショートカットを動作させない。

## Bug Issueとの連携

### 作成

Failed の結果から、Bug Issueを作成できる。
作成時に、次を自動で入力する。編集もできる。

| Bugの項目 | 入力元 |
| --- | --- |
| タイトル | テストケース名と発生内容 |
| テスト対象 | テスト計画の対象バージョン |
| OS | テスト結果の実施環境 |
| 対象モデル | テスト結果の実施環境 |
| 再現手順 | テストケースの事前条件と手順 |
| 実際の結果 | テスト結果 |
| 期待結果 | テストケース |
| 添付ファイル | テスト結果 |
| 元のテスト結果 | 自動でリンクする |

### 既存Bugの関連付け

新しいBugを作らずに、既存のBug Issueをテスト結果へ関連付けられる。
複数のテスト結果を、同じBug Issueへ関連付けられる。

### 修正後の再テスト

関連するBugが修正済みになったら、元の Failed の結果を上書きせず、新しい再テスト結果を作る。

```
1回目：Failed
  └─ Bug #123 を作成
Bug #123：修正済み
  └─ 再テスト要求
2回目：Passed
```

履歴で、1回目の Failed と2回目の Passed の両方を確認できる。

Bugの状態を変えても、テスト結果を自動で Passed にしない。

## 集計と進捗表示

### 件数

テスト計画に、次の件数を表示する。

全件数、Passed、Failed、Blocked、Skipped、Not Applicable、Not Run、Retest Required

### 進捗率

```
進捗率 = 実施済み件数 ÷ 実施対象件数 × 100
実施済み件数 = Passed + Failed + Blocked + Skipped
実施対象件数 = 全件数 − Not Applicable
```

### 合格率

```
合格率 = Passed ÷ 判定済み件数 × 100
判定済み件数 = Passed + Failed
```

Blocked、Skipped、Not Applicable、Not Run は、合格率の分母に含めない。

### 表示

件数、割合、色の凡例を同時に表示する。
色だけで結果を区別せず、アイコンか状態名を併記する。

```
Progress  32 / 40  80%
Passed    25
Failed     4
Blocked    2
Skipped    1
Not Run    8
```

## 履歴

テスト計画の履歴として、次を記録する。

- 作成
- テストケースの追加・削除
- 対象バージョン・環境の変更
- 状態の変更
- 完了・再開

テスト結果の履歴として、次を記録する。

- 結果を記録したユーザーと日時
- 変更前と変更後の結果
- コメント、添付ファイル
- 関連付けたBug
- 再テストとの関係

過去の結果は、削除も上書きもせず、変更履歴として参照できるようにする。

## 初期リリースの範囲

### 含める

- テストケースの作成・編集
- テスト計画の作成と、テスト計画へのケース追加
- Passed、Failed、Blocked、Skipped、Not Applicable の記録
- コメントと添付ファイル
- 結果の保存後に、次のケースへ移動
- 件数と進捗率の表示
- Failed の結果からのBug Issue作成と、既存Bugの関連付け
- 過去のテスト結果の保持
- Bug修正後の再テスト結果の追加

### 含めない

- AIによるテストケース生成
- テストケースのレビュー・承認ワークフロー
- 高度な権限管理
- Power BI などによる高度な分析
- 外部テスト管理サービスとの双方向同期
- 自動テストの実行
- CI/CDからのテスト結果の自動登録
- 複数プロジェクトを横断するレポート
- テストケースのパラメーター化
- テストケースの正式なバージョン管理

## 参考にする既存ツール

画面と操作は、既存ツールを実際に操作して記録してから設計する。手順は[進捗管理の作業規則](../AGENTS.md#ui設計)に従う。

- Qase：テスト実施画面、結果入力、進捗表示。テストケースはSuiteに所属し、Test Runを通じて結果を記録する
- TestRail：テストケース、Test Run、Test Plan、結果、Defectを分離する情報構造
- Azure Test Plans：Requirement、Test、Build、Bug、再テストの関連付け。テスト中に作成したBugへ、診断情報や対象Buildを関連付けられる
- GitHub Projects：IssueとPull Requestの管理
