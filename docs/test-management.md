# テスト管理の仕様

対象読者は、テスト管理機能の設計者と実装者。
対象範囲は、テストケース、テスト計画、テスト結果、Bug連携、集計の仕様。
読むと、保存する情報、画面で扱う情報と操作、リリースごとの範囲と対象外を確認できる。
次のリリースで追加する機能も、仕様として本文に書く。どのリリースで提供するかは、[リリースの範囲](#リリースの範囲)に従う。

範囲外は、画面の配置と見た目（UI設計の手順に従って別に決める）、テーブルなど物理的なデータ構造、AIによるテストケース生成。画面については、表示する情報と操作の要件だけを定める。
保存の方式は[保存](#保存)に従い、この仕様で定める情報と履歴を保持できることを要件とする。

## 目的

テストについて、次を一貫して管理する。

- 再利用できるテストケースの定義
- バージョンと実施条件（OS環境、対象モデル）を指定したテスト計画
- テストケースごとの実施結果
- 実施状況と合格・不合格の集計
- 不合格の結果からのBug Issue登録
- Bug修正後の再テスト
- 過去の実施結果の参照

テストケースの内容と、特定バージョンに対する実施結果は、別の情報として管理する。

## 情報の構造

```
テストケース
  ↓ 選択
テスト計画
  ↓ 実施
テスト結果
  ↓ 必要に応じて
Bug Issue
  ↓ 修正後
再テスト結果
```

| 情報 | 内容 |
| --- | --- |
| テストケース | 何を、どの手順で確認するかの定義。複数のテスト計画から再利用する |
| テスト計画 | 特定のバージョンと実施条件（OS環境、対象モデル）に対して実施するテストケースの集合 |
| テスト結果 | テスト計画内の各テストケースの実施結果。結果を記録または訂正しても、テストケースの定義は変えない |
| Bug Issue | テストで見つかった問題。作成元のテスト結果と相互に参照できる |

同じテストケースを異なるバージョンや環境で実施する場合は、別のテスト結果を作る。
再テストでは、既存の結果を訂正せず、新しいテスト結果を作る。

## テストケース

### 項目

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| ID | ○ | テストケースを一意に識別するID |
| タイトル | ○ | 確認内容を端的に示す名称 |
| 目的 | | このテストで確認する内容 |
| 事前条件 | | 実施前に満たす条件 |
| 手順 | ○ | 実施する操作 |
| 期待結果 | ○ | 正常な場合に得られる結果 |
| 事後処理 | | テスト後に必要な復旧・終了操作 |
| カテゴリ | | 機能、画面、コンポーネントなどの分類 |
| 優先度 | | High、Medium、Low |
| テスト種別 | | Manual、Automated、Exploratory など |
| 状態 | ○ | Active、Draft、Deprecated |
| 関連する仕様 | | GitHub Issue、仕様書、要件への参照 |
| 備考 | | 補足 |

### 状態

| 状態 | 意味 |
| --- | --- |
| Draft | 作成中。通常のテスト計画には追加しない |
| Active | 実施できる |
| Deprecated | 廃止済み。履歴のために保持する |

### 変更

テストケースを変更しても、過去のテスト結果に記録された内容を、変更後の内容で上書きしない。

## テスト計画

### 項目

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| ID | ○ | テスト計画を一意に識別するID |
| 名前 | ○ | 計画の名称 |
| 目的 | | テスト対象と実施目的 |
| 対象バージョン | ○ | テスト対象のソフトウェアのバージョン |
| 対象ビルド | | 予定するビルド番号 |
| 実施条件 | ○ | 予定するOS環境（OSとOSバージョン）と対象モデルの組。複数指定できる。例：Windows 11 24H2 / Model A、macOS 15.1 / Model A、macOS 15.1 / Model B。モデルを必要としないテストのために、対象モデルは「なし（共通）」を選べる |
| 担当者 | | テスト計画全体の担当者 |
| 開始日 | | テスト開始日 |
| 完了日 | | テスト完了日 |
| 状態 | ○ | Draft、In Progress、Completed、Archived |
| テストケース | ○ | この計画で実施するケース |
| 関連Issue | | リリース、Feature、Requirement などへの参照 |

テスト計画の対象バージョン、対象ビルド、実施条件は、予定しているテスト条件を表す。
実施条件は組で指定し、OS環境と対象モデルの全組み合わせには展開しない。
テスト結果の対象ビルドと実施環境は、実際にテストした条件を表す。
実際の条件が計画と異なる場合も、テスト結果には実際の条件を記録する。
環境によって結果が変わる場合は、実施条件をテスト計画に明示する。

### 状態

| 状態 | 意味 |
| --- | --- |
| Draft | ケースの選択と条件の設定中 |
| In Progress | テストを実施中 |
| Completed | 必要なテストが完了している |
| Archived | 過去の記録として保管している |

### テストケースの追加

テスト計画には、Active状態のテストケースを追加できる。

初期リリースでは、次の方法で追加できる。

- テストケース一覧から個別に追加する
- 複数のテストケースを一括で追加する
- カテゴリで絞り込んで追加する

次のリリースでは、過去のテスト計画から複製して追加できる。

追加した時点では、計画の実施条件（OS環境、対象モデルの組）ごとに、各テストケースの結果を Not Run にする。
Not Run の間は、実施者と実施日時を設定しない。

### 計画内のケース

計画へ追加したケースは、再利用するテストケース自体とは別に、次の項目を持つ。

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| 担当者 | | この計画で、このケースを実施する担当者 |

### 削除

- テスト結果に使われたテストケースは削除できない。不要になったら Deprecated にする。
- テスト結果が記録されたテスト計画は削除できない。不要になったら Archived にする。
- 結果のないテストケースとテスト計画を、Draft のときに削除できるかは、[未決定事項](#未決定事項)で決める。

## テスト結果

### 単位

テスト結果は、テスト計画内のテストケースと実施条件（OS環境、対象モデルの組）の組み合わせごとに作る。

```
テスト計画
  └─ テストケース
      ├─ Windows 11 / Model A の結果
      ├─ macOS 15 / Model A の結果
      └─ macOS 15 / Model B の結果
```

件数と進捗率は、この組み合わせを単位に数える。
結果別の件数では、各組み合わせの最新の結果を数える。
過去に Failed があり、最新の結果が Passed ではない組み合わせは、再テスト状態または結果履歴から確認できるようにする。関連Bugがある場合は、あわせて表示する。
最新の結果が Blocked の場合、結果別の件数では Blocked として数え、過去の Failed は結果履歴に表示する。

### 状態

| 状態 | 意味 |
| --- | --- |
| Not Run | 未実施 |
| Passed | 期待結果を満たした |
| Failed | 期待結果を満たさなかった |
| Blocked | 外部要因により実施または判定できなかった |
| Skipped | 本来は対象だが、今回は実施しなかった |
| Not Applicable | 今回の環境や対象モデルでは対象外 |

SkippedとNot Applicableは区別する。

### 再テスト状態

再テストが必要かどうかは、結果とは別の再テスト状態で表す。
結果が Failed のまま、再テスト状態を Required にできる。

| 再テスト状態 | 意味 |
| --- | --- |
| Not Required | 再テストは不要 |
| Required | 再テストが必要 |
| Completed | 再テストの結果を記録済み |

再テスト状態は、次の規則で変える。

- 結果を Not Run で作成した時点では、再テスト状態を Not Required にする。
- 再テストの結果を記録したら、元の結果の再テスト状態を Completed にする。
- 新しい結果の再テスト状態は、Not Required を初期値にする。さらに再テストが必要な場合は、Required にする。
- 再テスト対象件数では、各組み合わせの最新の結果のうち、再テスト状態が Required のものを数える。

```
1回目  結果：Failed   再テスト状態：Completed
2回目  結果：Blocked  再テスト状態：Required
3回目  結果：Passed   再テスト状態：Not Required
```

初期リリースでは、Bugの状態変更と再テスト状態を連携しない。
利用者が、対象のテスト結果の再テスト状態を Required に変更する。
自動の通知と、再テスト一覧への追加は、[未決定事項](#未決定事項)で決める。

### 項目

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| テスト計画 | ○ | 所属するテスト計画 |
| テストケース | ○ | 実施したテストケース |
| 結果 | ○ | Passed、Failed など |
| 実施者 | 実施後は必須 | 結果を記録したユーザー。Not Run では未設定 |
| 実施日時 | 実施後は必須 | 結果を記録した日時。Not Run では未設定 |
| 実際の結果 | Failed のとき必須 | 実際に起きた動作 |
| コメント | | 補足 |
| 添付ファイル | | スクリーンショット、ログなど。次のリリースで提供する |
| 関連Bug | | この結果から作成したBug。既存Bugの関連付けは、次のリリースで提供する |
| 再テスト状態 | ○ | Not Required、Required、Completed |
| 再テスト元 | | 再テストのとき、前回の結果 |
| 対象ビルド | | 実際にテストしたビルド |
| 実施環境 | | 実施時のOS環境、対象モデル |
| テストケースの内容 | 確定後は必須 | 確定してコピーしたタイトル、目的、事前条件、手順、期待結果、事後処理。[保存](#保存)に従う |

### Passed の記録

Passed は、最小の操作で記録できるようにする。
操作は、Passed を選び、保存し、次の未実施ケースを表示する、の順。
Passed では、コメントも添付ファイルも求めない。

### Failed の記録

Failed を選んだときは、次を入力できる。

- 実際の結果（必須）
- コメント
- スクリーンショット、ログ（次のリリース）
- 関連する既存Bug（次のリリース）
- 新しいBugの作成

Bug Issueの作成は必須にしない。
既知の問題、仕様の確認中、重複などの理由で、作らない場合があるため。

## テスト実施画面

### 表示

画面には、次を表示する。

- テストケース一覧：名称、現在の結果、担当者、関連Bugの有無、再テストの要否
- 選択中のテストケース：タイトル、目的、事前条件、手順、期待結果、関連する仕様、過去の結果
- 結果入力：結果の選択、実際の結果、コメント、Bugの作成。添付ファイルと既存Bugの関連付けは、次のリリースで提供する

結果を保存したあとは、次の未実施ケースへ移動できる。

### キーボード操作

キーボード操作は、次のリリースで提供する。
結果を繰り返し入力するため、キーボードだけで結果の選択と移動ができるようにする。
入力欄に文字を入力しているときは、結果を変えるショートカットを動作させない。
割り当てるキーは、[候補](#キー割り当ての候補)から決める。

## Bug Issueとの連携

### 作成

Failed の結果から、Bug Issueを作成できる。
作成時に、次を自動で入力する。編集もできる。

| Bugの項目 | 入力元 |
| --- | --- |
| タイトル | テストケース名と発生内容 |
| 対象バージョン | テスト計画の対象バージョン |
| 対象ビルド | テスト結果の対象ビルド |
| OS環境 | テスト結果の実施環境 |
| 対象モデル | テスト結果の実施環境 |
| 再現手順 | テスト結果に保存したテストケースの事前条件と手順 |
| 実際の結果 | テスト結果 |
| 期待結果 | テスト結果に保存したテストケースの期待結果 |
| 添付ファイル | テスト結果（次のリリースで提供） |
| 元のテスト結果 | 自動でリンクする |

### 既存Bugの関連付け

既存Bugの関連付けは、次のリリースで提供する。
新しいBugを作らずに、既存のBug Issueをテスト結果へ関連付けられる。
複数のテスト結果を、同じBug Issueへ関連付けられる。

### 修正後の再テスト

関連するBugが修正済みになったら、元の Failed の結果を上書きせず、新しい再テスト結果を作る。

```
1回目：Failed
  └─ Bug #123 を作成
Bug #123：修正済み
  └─ 利用者が、1回目の再テスト状態を Required にする
2回目：Passed
  └─ 1回目の再テスト状態：Completed
  └─ 2回目の再テスト状態：Not Required
```

履歴で、1回目の Failed と2回目の Passed の両方を確認できる。

Bugの状態を変えても、テスト結果を自動で Passed にしない。

## 集計と進捗表示

### 件数

テスト計画に、次の件数を表示する。

全件数、Passed、Failed、Blocked、Skipped、Not Applicable、Not Run

あわせて、各組み合わせの最新の結果のうち、再テスト状態が Required の件数（再テスト対象件数）を、結果別の件数とは別に表示する。
0件の状態も件数に含める。画面で0件の状態を省略できるかは、UI設計で決める。

### 進捗率

次の式は暫定である。BlockedとSkippedを実施済みに含めるかは、[未決定事項](#未決定事項)で決める。
Not Runは、未実施として数える。再テスト状態は、進捗率に影響しない。

```
進捗率 = 実施済み件数 ÷ 実施対象件数 × 100
実施済み件数 = Passed + Failed + Blocked + Skipped
実施対象件数 = 全件数 − Not Applicable
```

### 合格率

```
合格率 = Passed ÷ 判定済み件数 × 100
判定済み件数 = Passed + Failed
```

Blocked、Skipped、Not Applicable、Not Run は、合格率の分母に含めない。

### 表示

件数、割合、色の凡例を同時に表示する。
色だけで結果を区別せず、アイコンか状態名を併記する。

```
Progress  32 / 40  80%
Passed            25
Failed             4
Blocked            2
Skipped            1
Not Applicable     0
Not Run            8
再テスト対象        3
```

## 履歴

テスト計画の履歴として、次を記録する。

- 作成
- テストケースの追加・削除
- 対象バージョン・実施条件の変更
- 状態の変更
- 完了・再開

テスト結果の履歴として、次を記録する。

- 結果を記録したユーザーと日時
- 変更前と変更後の結果
- コメント、添付ファイル（添付ファイルは次のリリース）
- 関連付けたBug
- 再テストとの関係

過去のテスト結果は削除しない。
訂正したときは、訂正後の内容を現在の結果として表示し、訂正前の内容も変更履歴から参照できるようにする。
再テストを実施したときは、元の結果を訂正せず、新しいテスト結果を作って元の結果と関連付ける。

結果の変更履歴と再テスト結果は、別の情報として扱う。
入力ミスを Failed から Passed へ訂正することと、修正版をテストして新しく Passed を記録することは、意味が異なる。

## 保存

テストケース、テスト計画、テスト結果は、バグ管理とは別のSQLite DBに保存する。
ケース編集の接続・復旧方法は[テストケースの登録・編集](test-case-editor.md)に従う。
初期リリースでは、[バグ報告ツール](bug-reporting.md#報告と再現データの保存)と同じ、Nodeのローカルモードで使う。クラウドモードには組み込まない。

GitHubへ書き込むのは、Failed の結果からのBug Issueの作成だけにする。
テストケース、テスト計画、テスト結果はGitHubに書かない。

テスト結果は、テストケースの内容のコピーを持つ。

- 計画内のケースごとに、最初の結果を記録した時点で、テストケースの内容（タイトル、目的、事前条件、手順、期待結果、事後処理）を確定してコピーする。カテゴリ、優先度、状態などの分類はコピーしない。
- 同じ計画で、同じケースを別の実施条件で実施するときは、確定した内容を使う。
- 確定する前の Not Run は、テストケースの最新の内容を表示する。
- 確定したあとにテストケースを変更しても、記録済みの結果の内容は変わらない。

## リリースの範囲

段階的にリリースする。初期リリースでは、テストを計画し、結果を記録し、不合格をBugへつなげて再テストするまでの最小の流れを提供する。

### 初期リリースに含める

- テストケースの作成・編集・廃止
- テスト計画の作成と、テスト計画へのケース追加
- ケースごとの担当者の設定
- Passed、Failed、Blocked、Skipped、Not Applicable の記録
- 実際の結果とコメントの記録
- 結果の保存後に、次のケースへ移動
- 結果別の件数と進捗率の表示
- Failed の結果からのBug Issue作成と、元のテスト結果との相互リンク
- 再テスト結果の追加
- 過去のテスト結果の参照

### 次のリリースで追加する

- 添付ファイル
- 既存Bugの検索と関連付け（複数の結果を同じBugへ関連付けることを含む）
- キーボードショートカット
- 過去のテスト計画からの複製
- 担当者による絞り込み

### 含めない

- AIによるテストケース生成
- テストケースのレビュー・承認ワークフロー
- 高度な権限管理
- Power BI などによる高度な分析
- 外部テスト管理サービスとの双方向同期
- 自動テストの実行
- CI/CDからのテスト結果の自動登録
- 複数プロジェクトを横断するレポート
- テストケースのパラメーター化
- テストケースの正式なバージョン管理

## 未決定事項

決定までは、この節に残す。決まったら、該当する本文へ移し、この節から消す。

| 区分 | 項目 | 現在の扱い |
| --- | --- | --- |
| 状態 | Skipped を実施済みに含めるか | 進捗率の式では含める。運用の意味を確認して決める |
| 状態 | Blocked を実施済みに含めるか | 進捗率の式では含める。運用の意味を確認して決める |
| 状態 | テスト計画を完了できる条件 | 未決定。初期案：Not Run の結果があるときは完了できない。Failed、Blocked、Skipped、再テスト対象があるときは、警告を表示して完了できる。完了後も再開でき、再開は履歴に残る |
| データ構造 | 再テストの結果が使うテストケースの内容。再テストを記録した時点の最新の内容にするか、元の結果の内容を使うか | 未決定 |
| Bug連携 | Bug Issueを作成する接続先のリポジトリと、GitHubへの操作範囲 | 未決定。ユーザーが決めてから、Bug作成を実装する |
| 削除 | 結果のないテストケースとテスト計画を、Draft のときに削除できるか | 未決定 |
| Bug連携 | Bugが修正済みになったときの再テストの通知方法 | 未決定。初期リリースは手動で Required にする。自動で Required にする、通知する、再テスト一覧に追加する、のいずれかを後で決める |
| Bug連携 | Bugを再オープンしたときの扱い | 未決定 |
| Bug連携 | 1つの結果に複数のBugを関連付けるか | 未決定 |
| UI | Passed を1クリックで保存するか | 未決定 |
| UI | 保存後に次のケースへ自動で移動するか。無効にできるようにするか | 移動できる。無効化は未決定 |
| UI | ケース一覧と実施画面を同時に表示するか | 未決定 |
| UI | 過去の結果を実施画面に常時表示するか | 未決定 |

## キー割り当ての候補

[キーボード操作](#キーボード操作)に割り当てるキーの候補。実際の画面で試してから決める。

| 操作 | キー |
| --- | --- |
| Passed | P |
| Failed | F |
| Blocked | B |
| 次のケース | ↓ または J |
| 前のケース | ↑ または K |
| 保存 | Ctrl+Enter / ⌘+Enter |

## 参考にする既存ツール

画面と操作は、既存ツールを実際に操作して記録してから設計する。手順は[進捗管理の作業規則](../AGENTS.md#ui設計)に従う。
以下の特徴は、仕様の依頼者が示した内容であり、実画面では未確認である。

- Qase：テスト実施画面、結果入力、進捗表示。テストケースはSuiteに所属し、Test Runを通じて結果を記録する
- TestRail：テストケース、Test Run、Test Plan、結果、Defectを分離する情報構造
- Azure Test Plans：Requirement、Test、Build、Bug、再テストの関連付け。テスト中に作成したBugへ、診断情報や対象Buildを関連付けられる
- GitHub Projects：IssueとPull Requestの管理
