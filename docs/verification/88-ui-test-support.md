# 画面テストの共通化の検証

開発者とレビュー担当者が、[#88](https://github.com/Wakua/github-progress-board/issues/88) の移行範囲と、既存テストの判定を保ったことを確認するための記録である。
製品の画面や保存処理は変更していない。

## 対象と設計

- 比較元：`b49f56166fd11e32575842f1dc2121c5fd2a41ac`
- 検証・自己レビュー対象：`e9f1d369241f2532cf2392e6599ff685ca897149`
- 実施者：Codex、2026-11-03（JST）
- 環境と実行時刻、結果の抜粋：[検証データ](88-ui-test-support.json)

Issue作成時は対象数が実態と合っていなかった。
現行mainで同じ読み込み処理を持つ10ファイルと、部品の擬似DOMを持つ2ファイルを調べ、Issueの対象を12ファイルにそろえた。
前提のPR #83・#84・#86 はマージ済みで、着手時に対象を変更する開いたPRはなかった。

[共通部品](../../tests/support/bug-ui.mjs)に、DOM要素、fixtureごとの要素検索とフォーカス、appの読み込みを置いた。
API応答、利用者の権限、報告データ、タイマー、各テストの判定は呼び出し側に残した。
既存の絞り込み部品の模擬は、そのまま利用する。

共通の読込処理は名前付きimportを取り除き、末尾の自動起動より前を実行する。
複数行、字下げ、単一・二重引用符、LF・CRLFを受け付ける。
対応していないimport構文や、失われた起動境界は読み込み時に失敗させる。
製品側のimportや自動起動は変更していない。

## 検証結果

| 検証 | 結果 | 確認した内容 |
| --- | --- | --- |
| 変更前の12ファイル | 118件成功 | 比較元の結果を取得 |
| 変更後の12ファイルと共通部品 | 124件成功 | 既存118件と追加6件。失敗・skipなし |
| 実際のappのimport形式を変更 | 118件成功 | 10ファイルの読込側を直さず、複数行・二重引用符・字下げ・CRLFで実行 |
| `npm test` | 808件成功 | 全体の回帰。失敗・skipなし |
| `npm run check`、`git diff --check` | 成功 | 共通部品を含む構文、画像の規則、差分の空白 |

import形式の検証では、専用worktreeの `dist/bugs/app.mjs` を一時的に書き換えた。
検証後は元のバイト列へ戻し、SHA-256とGit差分で復元を確認した。
比較元と提出版の `dist/`、`server/`、`server.mjs` に差分はない。

[追加テスト](../../tests/bug-ui-support.test.mjs)は、import形式を変えても実際の一覧を描けること、自動起動のAPIを呼ばないこと、境界の異常を検出することを確認する。
DOMとフォーカスがfixture間で混ざらず、詳細を描き直した際に古い要素を返さないことも確認した。
既存118件のテスト名と成功結果を照合し、判定式はクラス状態・フォーカスの参照先を除いて一致することを確認した。

初回の移行後は、かんばん2件が旧擬似DOMの `classes.has` 参照で失敗した。
共通部品の `classList.contains` に合わせ、判定対象を保って修正した。
追加テスト3件は架空報告のGitHub状態が不足していたため補った。
修正後に上表の検証を実施した。

## 再実行

Node.jsと、全体テストが使うPython・jsonschemaを利用できる環境で実行する。
基本の手順は[起動と検証](../../README.md#起動と検証)に従う。
今回のNode.jsの版は検証データに記録した。

```powershell
$uiTests = @(
  'search-ui', 'refresh-ui', 'workflow-ui', 'text-ui',
  'reporting-form', 'category-ui', 'kind-ui', 'board',
  'thread', 'decision-ui', 'tag-roles', 'filter-panel'
) | ForEach-Object { "tests/bug-$_.test.mjs" }
node --test @uiTests tests/bug-ui-support.test.mjs
npm test
npm run check
```

import形式の再確認は、共通部品の追加テストで通常の `npm test` に含まれる。
実際のappファイルを書き換えて行った118件の結果は検証データの `import-format` に記録した。

## 自己レビュー

### 確認範囲

比較元と対象版の15ファイルの差分と共通部品の全文を読み、呼び出し元12ファイルのfixture・判定と、製品側のDOM操作・import・自動起動を照合した。
検索の遅延と古い応答、タグ取得の失敗、送信の途中失敗、カテゴリ・種別・要望判定、詳細から戻る操作の判定を削っていないことを確認した。
フォーカスの参照はクラスの共有状態からfixtureの `document.activeElement` に変え、同じ要素へ移る判定を保った。

この記録はIssueの完了条件、READMEの「起動と検証」、開発手順の「PRに残す証拠」、UIレビューの適用範囲と照合した。
製品仕様をこの文書へ再定義していない。
提出時には、文書の表示とPRからの参照も確認する。

### 指摘

上記の移行時の失敗は修正し、再確認した。

### 未確認の範囲

擬似DOMは、テストが使う操作だけを表す。
レイアウト、イベントの伝播、ブラウザによるフォームの既定動作は扱わない。
今回の変更はテスト基盤に限るため、実画面の観察、比較画像の追加、ブラウザ検証の再実行は対象外とした。
製品全体の動作の受入確認は、ユーザーの指定どおりリリース時に行う。
