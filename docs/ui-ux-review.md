# UI/UXレビューの手順

画面の追加・変更を担当する人とAIが、提出前の問題を見つけ、修正と再確認の根拠を残すための手順である。
配置・表示・文言・操作の流れを変える試作も対象とし、この手順で提出の可否を判断する。
製品の仕様や画面案の採用は、このレビューだけでは決めない。

## 参照する規則

画面の情報量は[方針](../AGENTS.md#方針)、観察と試作は[UI設計](../AGENTS.md#ui設計)、画像は[保存の規則](screenshots.md)に従う。
提出時に使う問いは[必須の問い](ui-review-questions.md)を正本とする。
個人端末の学習メモは、背景を調べる補足資料として使う。
メモの配置や有無によって、必須の問いを変えない。

## 確認の進め方

1. 対象の版、画面・状態、表示条件を決める。
   利用者の目的、判断に必要な情報、次の操作を画面の箇所に対応させる。
2. mainにある必須の問いを読み、各IDをPRの指摘表へ記す。
   関係する追加の問いがあれば行を加える。
   学習メモ01〜03の全文を毎回読むことや、個人端末のパスをCIから参照することは必須にしない。
3. 次の3項目と、変更に関係する問いを実画面で確かめる。
   情報量、判断の手掛かり、操作は別々に判定し、一つの確認でほかも合格にしない。
4. 指摘を修正し、同じ条件で再確認する。
   追加・修正した箇所だけでなく、影響する画面全体で重複と操作のつながりを見直す。

情報量の確認を「詳細を開けるか」に置き換えない。
同じ目的の説明の重複と、文字・記号・色など役割が異なる表示を区別する。
文字数は削減量の記録に使い、必要な情報を隠したり、使いやすさの合格基準にしたりしない。

原則の名前や学習メモの仮想例だけを、画面が使いやすい根拠にしない。
静止画での点検、実操作の成功、実利用者の理解は分けて記録する。
このレビューは、既存の観察、利用者による確認、ブラウザ検証に代わるものではない。

## 提出の判定

画面案を利用者へ提出する前と、PRをReadyにする前に、作業担当が対象版の記録を残す。
各項目は「確認済み」「要修正」「未確認」「対象外」で判定する。
根拠の書式と対象外にできる範囲は[記録の書式](#記録の書式)に従う。
同じ版の記録は参照してよいが、変更箇所と影響する操作は再確認する。

次のいずれかがあれば、レビュー完了やUI変更の完了を報告せず、PRをReadyにしない。

- リポジトリ内の必須の問いを読めない、またはレビュー記録がない。
- [PR本文への画像掲載条件](screenshots.md#prへの貼り方)を満たしていない。
- 変更の目的や規則に反する指摘が未修正である。
- 今回の変更に必要な確認が未実施である。
  重複・不要な常設説明の点検を「利用者の理解は未確認」に含めて先送りしない。

利用者の理解を確かめるための試作は、上記の条件を満たしたうえで、未確認の仮説と確認課題を添えて提出する。
利用者テストの課題では、達成したい結果を伝え、操作場所や正解を先に教えない。
観察した行動と、担当者が説明・誘導した後の結果を分ける。
背景を調べる場合は、学習メモ04の「ユーザビリティテストの課題設計」「観察と誘導の区別」を参照する。
点検の完了を、利用者の理解、画面案の採用、WCAGへの適合が確認できたこととして扱わない。

## 記録の書式

提出する版の判定と根拠は、PR本文の「UIレビュー」を正本とする。
詳細な観察・操作記録は既存の画面検討文書へ置いて参照できるが、判定表をリンクだけで代替しない。
PR作成前の記録をIssueや画面検討文書へ置いた場合は、提出時にPRへ移し、元の記録には参照を残す。
過去の版のレビュー記録を、最新の判定として扱わない。
画像は[PRへの貼り方](screenshots.md#prへの貼り方)に従い、PR本文とレビュー文書で同じ画像ファイルを使う。

### 確認範囲

- 対象版、画面・状態、表示条件。
- 利用者の目的 → 判断に必要な情報 → 次の操作。
- 必須の問いのIDと、追加した問いの出典。
- `UI変更: あり` と `対象版: <PRのhead SHA>` を独立した行に記す。
  UI変更がなければ `UI変更: なし` と `対象外の理由: <具体的な理由>` を記す。

### 指摘

| 項目 | 問い | 判定 | 根拠 | 対応と再確認 |
| --- | --- | --- | --- | --- |
| 情報量 |  |  |  |  |
| 判断の手掛かり |  |  |  |  |
| 操作 |  |  |  |  |

「問い」には[必須の問い](ui-review-questions.md)から項目ごとのIDを転記する。
変更に関係する問いは行を加える。
「根拠」には、次のどちらかと、そこから確かめた事実を記す。

- `画像: docs/screens/127/after-10-compact-day.jpg` のような、今回追加・更新し、PRの比較欄に掲載した画像のパス。
- `操作: 一覧で対象を選ぶ → 詳細を開いて閉じる → 元の行へフォーカスが戻る` のような、起点・操作・結果を含む手順。

「確認済み」とだけ書いた文、今回と無関係の画像名、操作結果のない手順は根拠にしない。
操作手順を根拠にする場合も、[比較画像の掲載](screenshots.md#prへの貼り方)は省略しない。
操作を「対象外」にする場合は `理由: 静的な配色見本で操作部を持たない` のように理由を記す。
UI変更の情報量と判断の手掛かりは対象外にできない。
指摘がなければ「対応と再確認」に「指摘なし」と記す。

### 未確認の範囲

未修正の指摘と未実施の確認について、理由、影響、次に確認する方法を記す。
最後に、提出できる範囲と、判断を保留する範囲を示す。

## CIによる検査

`UI review gate`がPRの作成・更新・本文編集・Ready化で記録を検査する。
Draftは「作業中・未判定」（neutral）とし、Ready化で必須検査を行う。
Readyで欠落・要修正・未確認が見つかった場合は失敗とし、担当者はDraftへ戻して修正する。
マージ前には最新の本文とheadで成功していることを確かめる。
同じPR・headでは一つのチェックを更新し、本文修正前の失敗を別チェックとして残さない。
旧形式の重複は、再検査中のチェックへ統合する。
記録の不備による失敗は`UI review gate`へ記録する。
実行ジョブは結果を書き込めた場合に成功とし、通信・権限などで書き込めなかった場合に失敗する。

[ui-review.yml](../.github/workflows/ui-review.yml)は`pull_request_target`で起動し、mainの版だけをcheckoutする。
その版の[実行コード](../scripts/run-ui-review.mjs)、[検査コード](../scripts/check-ui-review.mjs)、必須の問いを使う。
PR側のコードは実行せず、本文・変更ファイル・画像のGit treeをAPIで読む。
検査結果にはmainの版と対象のheadを記し、headのチェックとして登録する。
検査自体を変更したPRにも、マージ済みの規則を適用する。

CIは宣言、対象版、指摘表、問いのID、判定、根拠の書式、[画像の掲載条件](screenshots.md#prへの貼り方)を確認する。
UIと判定するパスは検査コードの`isUiPath`を正本とし、新しい実行コードも検査対象に含める。
計算・保存だけを変える場合も、対象パスなら表示・操作への影響を実画面で確認する。
対象外のパスから表示や操作が変わる場合も、担当者は「UI変更あり」と記す。

この検査は、操作を実行した事実や根拠の内容の正しさを証明しない。
画像の実表示、撮影した画面と提出版の対応、判断に必要な情報の過不足、利用者の理解は、担当者と確認者が根拠を開いて確かめる。
CI成功をUIレビュー全体の合格に読み替えない。

### 初回導入と検査コードの更新

候補コードの[回帰テスト](../.github/workflows/ui-review-tests.yml)は、書込み権限のない別workflowで行う。
この成功を`UI review gate`の合格として扱わない。

初回はmainに検査コードがないため、導入PR自身ではmainからの検査を実行できない。
導入PRでは回帰テストと差分を確認し、この未確認範囲を添えてマージ承認を求める。
必須チェックを先に設定した場合の一時解除も、対象PRと再設定の手順を示して承認を得る。
承認後に導入PRをマージし、mainの保護設定で`UI review gate`を必須チェックにする。
続けて検証用Draft PRで未判定、Ready化後の欠落による失敗、修正後の成功を確認し、保護設定と実行結果を導入PRへ記録する。
この確認まで初回導入を完了としない。

既存PRの再検査にはmainの`UI review`を手動起動し、PR番号を指定する。
GitHubの[必須チェック](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-status-checks-before-merging)、[pull_request_target](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request_target)、[Checks API](https://docs.github.com/en/rest/checks/runs#create-a-check-run)に従う。
