# バグ報告の仕様と運用

バグ報告はローカル版の `/bugs/` で受け付ける。本文、再現データ、対応状況、修正版の確認結果を同じサーバーへ保存する。GitHub連携は[GitHub登録](#github登録)の設定と操作範囲に従う。

## 利用者と接続

このPCでは「共通の利用者」として使い、ログイン、APIキーの入力、名前の選択を行わない。報告の作成、全報告と再現データの閲覧・追加、対応状況の更新、確認結果の送信、GitHub登録管理を同じ利用者で行う。利用者同士の権限を区別しない。

APIはこのPCの127.0.0.1へ接続する。
Hostと、送信された場合のOriginを検査する。
ブラウザから別オリジンへの接続は受け付けない。
別のPCやクラウドへ公開するための認証と配置は[小規模運用のIssue #16](https://github.com/Wakua/github-progress-board/issues/16)で別途決める。

バグ報告はNodeのローカルモードで使う。
ChatGPT Sitesのクラウドモードには報告APIを組み込まず、進捗画面から報告へのリンクも表示しない。
以前の保存先にある報告者情報や履歴は、データとして保持する。
公開する内容は[公開対象](development.md#公開対象)に従う。

## 報告と再現データの保存

本文、対応状況、確認履歴、添付の情報、GitHub登録待ちをSQLiteに保存し、添付本体は別ファイルへ保存する。
進捗の手動計画とは別の保存単位として扱う。
報告と登録待ちは同じトランザクションで確定し、GitHubの成功を報告の受付条件にしない。

保存先は `BUG_REPORTING_DATA_DIR` で指定し、省略時は起動したフォルダーの `.bug-reporting-data/` を使う。
配信フォルダー `dist/` の中には置かない。
独自の保存先をリポジトリ内に置く場合も、Git管理から除外する。

再現データは形式を制限せず、一報告合計1GiB・20ファイルを初期上限とする。
自動削除は行わない。
上限は[初期設定](#初期設定)の管理コマンドで変更する。
報告文、要求の形式、ファイル情報の制約は[API仕様](bug-reporting-api.md)に記載する。

ファイルは内部IDで保存し、元の名前から保存パスを作らない。受信中は一時ファイルとし、容量とSHA-256を確認してから確定する。報告には確定済みの添付だけを関連付ける。一覧では添付情報だけを読み、取得時に本体をストリームで送る。

送信途中で失敗した未完了ファイルは起動時に回復する。確定した未登録データは自動削除せず、報告フォームで選び直せる。保存済みデータを再送したり、容量へ二重に数えたりしない。ディスク上のファイルが欠けた場合は取得の成功を返さない。

同じ保存先を使うサーバーは一つだけ起動する。SQLiteのWALを共有フォルダーへ配置せず、利用環境間の共有はAPI経由で行う。

## GitHub登録

接続先は `BUG_REPORTING_GITHUB_REPO` の `owner/repository` またはGitHubのrepository URLで指定する。
既定は空で、未設定時は報告の受付とローカル保存だけを行う。
起動前に、登録先の公開範囲とghの権限を運用者が確認する。
公開repositoryへ登録した報告文は第三者も読める。

GitHubへの書き込みは、新しい報告用Issueの作成だけを許可する。
登録結果の照合とタグ表示に使うIssue・タグの読み取りを行う。
コメント、ClosedとReopen、タグの付け外し、Projectの登録・更新、添付本体のアップロードは行わない。
資格情報はサーバーのghだけで扱う。

保存した報告は設定したrepositoryへの登録待ちに入れ、サーバーが直列に処理する。設定する前の報告は自動登録せず、利用者が報告を選んで登録する。保存済みの接続先が現在の設定と違う報告は、登録管理の操作を拒否する。

Issue本文の先頭行に保存先の識別子と報告IDを記録し、作成前の探索と作成結果の照合に使う。
探索と照合は、新しい順のIssue一覧から、対応する識別子を持つIssueを探す。報告の受付より1時間以上古いIssueには遡らない。

作成要求を送る前に、必ず探索する。
一件見つかれば作成せずに関連付け、複数見つかれば自動で選ばずに結果未確認として止める。
古いバックアップを復元して、登録済みの報告が未登録に戻った場合も、登録の操作や自動の処理が同じIssueへ関連付ける。
探索に失敗したときは作成要求を送らず、利用制限なら待機し、それ以外は登録失敗とする。

作成中に応答が途切れた場合や再起動した場合は「作成結果が未確認」とし、自動で再作成しない。
照合で対応する識別子が一件だけなら関連付け、複数なら自動で選ばない。

GitHubは、作成したIssueを一覧に載せるまでに数秒かかる。
このため、作成要求を送ってから60秒が過ぎる前に始めた照合は、該当なしを確定しない。
該当なしからの再試行は、作成要求の60秒以上あとに始めた照合の結果を、利用者が確認した場合だけ受け付ける。
さらに、最新の照合結果と更新番号を検査する。
画面は、再度照合できる時刻を示す。

外部APIの処理まで含めた厳密な一回だけの作成は保証しない。
次の場合は、重複の可能性が残る。

- サーバーの停止後に、残ったghの作成要求が60秒を超えて完了する。
- 作成から数秒以内に、同じ報告を別の保存先の状態から登録する。

補足：検証用のrepositoryで作成直後に読み取ると、Issue一覧は3.1〜5.6秒、識別子による検索は3.7〜6.8秒のあとに初めて該当のIssueを返した。個別のIssue番号による取得は即時だが、結果未確認の報告は番号を持たない。検索は一覧より遅く、1分あたりの回数制限もあるため、探索には一覧を使う。

利用制限の待ち時間は保存先で共有し、再起動後も保持する。応答ヘッダーに従って待機し、結果未確認の報告は自動再試行の対象にしない。

## タグの表示と取得

関連付けたIssueのタグを登録直後と利用者の手動更新で取得する。取得済みの空配列は「タグなし」、取得前は「未取得」と表示する。取得に失敗した場合は前回の結果を保持し、現在の結果を確認できていないことを示す。

タグの取得は本文、添付、対応状況、確認結果を変更しない。一覧では対応状況、タグ、GitHub登録状況を重ねて絞り込む。GitHubのClosedを報告の確認完了へ変換しない。

## 修正後の確認

対応状況は、受付済み → 対応中 → 修正済み・公開待ち → テスター確認待ち → 確認完了の順に扱う。
確認対象の版は[APIの必須項目](bug-reporting-api.md#対応状況と確認)に従って指定する。
対応状況の更新はGitHubのIssueへ書き込まない。

確認結果には、実際に確認した版と「直った」「まだ起きる」を保存する。対象版で直った場合は確認完了、対象版でまだ起きる場合は対応中へ戻す。違う版での確認は履歴に残し、対応状況を変えない。

対応状況と確認履歴は同じトランザクションで保存する。更新番号と再送の扱いは[APIの条件](bug-reporting-api.md#対応状況と確認)に従う。GitHub取得の失敗でも保存済みの確認結果を保持する。

## 初期設定

実行環境は[READMEの起動手順](../README.md#起動と検証)に従う。保存先を初期化して起動する。

```powershell
npm run bug:init
npm start
```

初期化は既存のDBを上書きしない。既存の保存先を使う場合は再初期化せず、サーバーを起動する。ポートは[起動と検証](../README.md#起動と検証)に従って指定する。ブラウザでは起動したポートの `/bugs/` を開く。

GitHubを使う場合は、運用者が選んだrepositoryを設定して再起動する。次の値は形式の例で、実在の報告用接続先を示さない。

```powershell
$env:BUG_REPORTING_GITHUB_REPO = 'example/bug-reports'
npm start
```

容量と件数は次の管理コマンドで変更する。既存の添付は保持する。

```powershell
npm run bug:settings -- set-policy --max-bytes <合計容量のバイト数> --max-files <ファイル数>
```

## 人のテスターとAIの操作

人のテスターは「バグを報告」から本文、任意の版、再現データを送る。受付結果の報告を開き、本文と添付を確認する。受付後は詳細から再現データを追加する。

報告フォームは保存失敗と同じページ内での開き直しに対して入力を保持する。再読み込みでは未保存の本文を失う。確定した未登録データはサーバーから再取得して選び直せる。送信の応答が途切れた場合は、保存結果を確認してから再試行する。

CodexとClaudeなどのAIは[API仕様](bug-reporting-api.md)に従い、再送時は同じ受付キーを使う。別の実行環境から使うには、このPCのサーバーへ接続できることが必要となる。

## バックアップ

サーバーと管理コマンドを停止してから、保存先フォルダー全体をコピーする。DBと添付を別々の時点でコピーしない。復元は別の保存先へ行い、元の保存先を保持したまま報告と添付を確認する。

## 実装状況と未確認事項

ローカルでの共通利用、SQLite保存、再現データの追加・取得、GitHub登録・照合、タグ表示、修正版の確認を対象とする。APIのテストには実際の活動と無関係な架空の予約管理の報告を使い、GitHubの要求は模擬アダプターで検証する。

ブラウザの検証は、[開発と検証のPlaywright設定](development.md#ブラウザ検証)を使って `npm run test:bugs:browser` で実行する。
操作前後の画像はGit管理外の `references/bug-reporting-qa/` に保存する。

人のテスターによる評価、別環境のAIとの接続、外部公開、上限付近の容量・性能、運用としてのバックアップと復元は未確認である。管理先は[ロードマップ](bug-reporting-roadmap.md)から参照する。
