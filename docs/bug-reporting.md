# バグ報告の仕様と運用

バグ報告はローカル版の `/bugs/` で受け付ける。本文、再現データ、対応状況、修正版の確認結果を同じサーバーへ保存する。GitHub連携は[GitHub登録](#github登録)の設定と操作範囲に従う。

## 利用者と接続

このPCでは「共通の利用者」として使い、ログイン、APIキーの入力、名前の選択を行わない。報告の作成、全報告と再現データの閲覧・追加、対応状況の更新、確認結果の送信、GitHub登録管理を同じ利用者で行う。利用者同士の権限を区別しない。

APIはこのPCの127.0.0.1へ接続する。
Hostと、送信された場合のOriginを検査する。
ブラウザから別オリジンへの接続は受け付けない。
別のPCやクラウドへ公開するための認証と配置は[小規模運用のIssue #16](https://github.com/Wakua/github-progress-board/issues/16)で別途決める。

バグ報告はNodeのローカルモードで使う。
ChatGPT Sitesのクラウドモードには報告APIを組み込まず、進捗画面から報告へのリンクも表示しない。
以前の保存先にある報告者情報や履歴は、データとして保持する。
公開する内容は[公開対象](development.md#公開対象)に従う。

## 報告と再現データの保存

本文、対応状況、確認履歴、添付の情報、GitHub登録待ち、[登録前のカテゴリ](#登録前のカテゴリ)、[タグの役割](#カテゴリの設定)をSQLiteに保存し、添付本体は別ファイルへ保存する。
進捗の手動計画とは別の保存単位として扱う。
報告と登録待ちは同じトランザクションで確定し、GitHubの成功を報告の受付条件にしない。

保存先は `BUG_REPORTING_DATA_DIR` で指定し、省略時は起動したフォルダーの `.bug-reporting-data/` を使う。
配信フォルダー `dist/` の中には置かない。
独自の保存先をリポジトリ内に置く場合も、Git管理から除外する。

再現データは形式を制限せず、一報告合計1GiB・20ファイルを初期上限とする。
自動削除は行わない。
上限は[初期設定](#初期設定)の管理コマンドで変更する。
報告文、要求の形式、ファイル情報の制約は[API仕様](bug-reporting-api.md)に記載する。

ファイルは内部IDで保存し、元の名前から保存パスを作らない。受信中は一時ファイルとし、容量とSHA-256を確認してから確定する。報告には確定済みの添付だけを関連付ける。一覧では添付情報だけを読み、取得時に本体をストリームで送る。

送信途中で失敗した未完了ファイルは起動時に回復する。確定した未登録データは自動削除せず、報告フォームで選び直せる。保存済みデータを再送したり、容量へ二重に数えたりしない。ディスク上のファイルが欠けた場合は取得の成功を返さない。

同じ保存先を使うサーバーは一つだけ起動する。SQLiteのWALを共有フォルダーへ配置せず、利用環境間の共有はAPI経由で行う。

## GitHub登録

接続先は `BUG_REPORTING_GITHUB_REPO` の `owner/repository` またはGitHubのrepository URLで指定する。
既定は空で、未設定時は報告の受付とローカル保存だけを行う。
起動前に、登録先の公開範囲とghの権限を運用者が確認する。
公開repositoryへ登録した報告文は第三者も読める。

GitHubへの書き込みは、新しい報告用Issueの作成だけを許可する。
作成の要求には、[登録前のカテゴリ](#登録前のカテゴリ)として選んだタグの名前を含める。
登録結果の照合とタグ表示に使うIssue・タグの読み取りを行う。
コメント、ClosedとReopen、作成後のタグの付け外し、新しいタグの作成、Projectの登録・更新、添付本体のアップロードは行わない。
資格情報はサーバーのghだけで扱う。

保存した報告は設定したrepositoryへの登録待ちに入れ、サーバーが直列に処理する。設定する前の報告は自動登録せず、利用者が報告を選んで登録する。

保存済みの接続先が現在の設定と違う報告は、状態によって次のように扱う。

- 登録に失敗した報告は、登録の操作で現在の接続先へ付け替えて登録待ちに戻す。失敗した報告にIssueは作られていないため、重複は起きない。綴りの誤りなどで失敗した場合は、設定を直して再起動し、報告を選んで登録し直す。画面は再試行の前に、登録に使う現在の接続先と、失敗した接続先を示す。
- 登録済みの報告は、接続先を変えても再登録せず、タグも取得しない。Issueは増えない。
- 結果未確認の報告は、現在の接続先での照合も再試行も拒否する。作成を試した接続先へ設定を戻し、照合と確認を済ませてから接続先を変える。
- 登録待ちと作成中の報告は、登録管理の操作を拒否する。

Issue本文の先頭行に保存先の識別子と報告IDを記録し、作成前の探索と作成結果の照合に使う。
探索と照合は、新しい順のIssue一覧から、対応する識別子を持つIssueを探す。報告の受付より1時間以上古いIssueには遡らない。

作成要求を送る前に、必ず探索する。
一件見つかれば作成せずに関連付け、複数見つかれば自動で選ばずに結果未確認として止める。
古いバックアップを復元して、登録済みの報告が未登録に戻った場合も、登録の操作や自動の処理が同じIssueへ関連付ける。
探索に失敗したときは作成要求を送らず、利用制限なら待機し、それ以外は登録失敗とする。

作成中に応答が途切れた場合や再起動した場合は「作成結果が未確認」とし、自動で再作成しない。
照合で対応する識別子が一件だけなら関連付け、複数なら自動で選ばない。

GitHubは、作成したIssueを一覧に載せるまでに数秒かかる。
このため、作成要求を送ってから保留時間（60秒）が過ぎる前に始めた照合は、該当なしを確定しない。
保留時間は、一覧への反映の遅れの最大（補足の8.1秒）と、ghの要求の制限時間（30秒）を超える値にした。
該当なしからの再試行は、保留時間が過ぎたあとに始めた照合の結果を、利用者が確認した場合だけ受け付ける。
さらに、最新の照合結果と更新番号を検査する。
画面は、再度照合できる時刻を示す。
更新前の版から引き継いだ作成中と結果未確認の報告は、作成要求の時刻が分からないため、更新の時点を作成要求の時刻とみなす。

外部APIの処理まで含めた厳密な一回だけの作成は保証しない。
次の場合は、重複の可能性が残る。

- サーバーの停止後に、残ったghの作成要求が保留時間を超えて完了する。
- 作成から数秒以内に、同じ報告を別の保存先の状態から登録する。

補足：検証用のrepositoryで作成直後に読み取ると、Issue一覧は3.1〜5.6秒、識別子による検索は3.7〜6.8秒のあとに初めて該当のIssueを返した。#16 の測定では、反映の遅れは2.2〜8.1秒だった。個別のIssue番号による取得は即時だが、結果未確認の報告は番号を持たない。検索は一覧より遅く、1分あたりの回数制限もあるため、探索には一覧を使う。

利用制限の待ち時間は保存先で共有し、再起動後も保持する。応答ヘッダーに従って待機し、結果未確認の報告は自動再試行の対象にしない。

## タグの表示と取得

関連付けたIssueのタグを、登録直後と、画面の「更新」で取得する。
「更新」は、現在の接続先に登録済みの全報告のタグを、Issue一覧からまとめて取り直す。
一覧は1回に100件を返すため、報告ごとに取得するより要求が少ない。
一覧に載らなかった報告（作成の直後や、削除されたIssue）は、Issue番号で個別に取得する。
個別の取得は、登録の処理を待たせるため、1回の「更新」で10件までにする。超えた報告は取得失敗として前回のタグを残す。次の「更新」は、前回の続きから個別に取得するため、取れない報告が続いても、ほかの報告に順番が回る。
一覧を読めなかったときは、個別には取得せず、対象の全報告を取得失敗として扱う。

取得済みの空配列は「タグなし」、取得前は「未取得」と表示する。取得に失敗した場合は前回の結果を保持し、現在の結果を確認できていないことを示す。

タグの取得は本文、添付、対応状況、確認結果を変更しない。一覧の絞り込みは、[報告一覧と検索](#報告一覧と検索)に従う。GitHubのClosedを報告の確認完了へ変換しない。

## カテゴリの設定

GitHubのタグごとに、報告をカテゴリで見るための区分として、メインカテゴリ、サブカテゴリ、使わないのどれかを割り当てる。
割り当てはこのツールの保存先に持ち、利用者を区別せず共通の1組とする。
タグ名の規則は設けず、GitHubのタグは変更しない。

割り当ての対象は、GitHubのタグのidで識別する。
GitHubでタグの名前を変えても割り当ては残り、画面には最後に取得した名前を表示する。
タグを削除して同じ名前で作り直すと、別のタグとして未設定から始まる。

GitHubから読めるのは、報告用のIssueと、[登録前のカテゴリ](#登録前のカテゴリ)の確認で名前を指定する1件のタグだけで、repositoryのタグ一覧は読めない。
設定の対象は、取得済みの報告に付いているタグである。取得に失敗して前回の結果を保持している報告のタグも含む。
どの報告にも付いていないタグは一覧に出ないが、保存した割り当ては残り、そのタグが付いた報告が現れると戻る。

割り当てを一度も保存していないタグを、未設定とする。
画面は未設定のタグの役割を「使わない」と表示し、新しいタグとして数える。
保存すると、設定画面に出ているすべての新しいタグが、選んだ役割（初期値は使わない）で確定する。
使わないで確定したタグは、新しいタグに数えない。

設定は、一覧の見出しの横の「カテゴリの設定」から開く。利用者を区別せず、誰でも開ける。
新しいタグがあるときだけ、開く操作に件数を添える。件数は、報告の一覧を読み込むたびに数え直す。
設定画面は、新しいタグを先頭に並べる。
保存の対象は、設定画面に出ているタグのうち、新しいタグと、役割を変えたタグだけである。設定画面を開いている間に増えたタグは、見せていないので確定しない。
ほかの人が同時に変えた割り当てを、変えていないタグで上書きしない。
要求と応答は[API仕様](bug-reporting-api.md#タグの役割)に従う。

## 登録前のカテゴリ

報告ごとに、GitHubへ登録する前のカテゴリを、GitHubのタグのidで保存する。
選べるのは、[カテゴリの設定](#カテゴリの設定)でメインかサブを割り当てたタグである。
報告フォームで選び、報告を作成するAPIでも指定する。要求と応答は[API仕様](bug-reporting-api.md#登録前のカテゴリ)に従う。

選んだカテゴリは、登録待ちと登録失敗の報告の詳細で選び直せる。
作成中と結果未確認の報告は、Issueの作成の要求がすでに送られた、または送られた可能性があるため、変えられない。登録済みの報告のカテゴリは、GitHubでタグを付けて変える。

Issueの作成の要求には、選んだタグの名前を含める。
要求を送る前に、名前ごとにタグを1件ずつ読み、同じidのタグがGitHubにあることを確かめる。次のタグは、要求に含めない。

- 名前を変えられた、または削除されたタグ
- 削除して同じ名前で作り直された（idが違う）タグ
- 付いている報告がなくなり、ツールが名前を知らなくなったタグ

GitHubは、存在しない名前のタグを指定されると、新しいタグを作って付ける。要求に存在しない名前を含めて、意図しないタグを作らないための確認である。
読み取りに失敗したときは、Issueを作らず、[登録の失敗](#github登録)として扱う。利用制限なら待機する。

登録後に初めてタグを取得できたとき、選んだタグがIssueに付いているかを確かめる。付いていないタグは、GitHub登録の欄に示す。
示すのは次の取得までで、その後に開発者がタグを付け替えても示さない。

登録前の報告の領域とカテゴリの絞り込みには、保留したカテゴリを使う。登録後は、GitHubのタグを使う。

## 報告一覧と検索

一覧の1件は、題名と対応状況を出す。題名は報告文の先頭行で、長いときは2行まで表示する。メインかサブを割り当てたカテゴリを持つ報告は、題名の下に領域を添える。カテゴリは、登録前の報告では[保留したカテゴリ](#登録前のカテゴリ)、登録後の報告ではGitHubのタグである。領域は、メインを「・」で並べ、サブを「 / 」の後ろに並べる。例：「予約・通知 / 一覧」。Issueと紐付いた報告は、題名の左に「#番号」を小さく添える。紐付いていない報告には出さない。番号は行の中では文字だけで、GitHubで開くリンクは詳細にある。報告者、受付日時、再現データの件数、すべてのタグは、詳細で確認する。

GitHubの接続が有効で、GitHub登録が完了していない報告だけ、対応状況の下に登録状況の印を出す。接続が無効なときは登録が始まらないため、印を出さない。

幅761px以上では、一覧の右に詳細を並べる。一覧をスクロールしても、詳細は画面の上に残り、報告を選ぶたびに上へ戻る必要がない。詳細が画面より長いときは、詳細の中だけをスクロールする。幅760px以下では、一覧と詳細を切り替える。

一覧の上に、検索欄、メイン、サブ、対応状況、GitHub登録の順に絞り込みを並べる。すべて重ねて使える。

- メインとサブは、[カテゴリの設定](#カテゴリの設定)で割り当てたタグから選ぶ。別々の軸で、サブはメインを選ばなくても選べる。
- 対応状況の選択肢に、確認完了だけを外してほかの状況を出す「確認完了を除く」を置く。開いたときの既定は「すべての状況」である。
- 選択肢の括弧の数は、未対応（受付済みと対応中）の件数である。メインは、未対応の報告がなくても、件数0で出す。報告に付いていないタグは、設定の対象にならないため、選択肢にも出ない。
- サブの選択肢は、選んだメインの報告に付いているサブだけを出す。メインを変えて、選んでいたサブがなくなったときは「すべて」に戻す。
- メインの選択肢に「未分類」を置く。メインとサブのどちらのカテゴリも持たない報告を出す。タグを取得できていない報告と、カテゴリを選んでいない登録前の報告を含む。サブだけを持つ報告は含めず、サブで探す。
- タグの取得に失敗して前回の結果を保持している報告は、その結果で分ける。
- 領域と選択肢の名前は、カテゴリの設定に出る、最後に取得した名前を使う。
- カテゴリの設定を保存すると、選択肢と行の領域を、新しい割り当てで描き直す。タグの役割を読み込めなかったときは、理由を通知し、前回の割り当て（なければ未設定）のまま表示する。

一覧の上の検索欄に語を入れると、本文にその語をすべて含む報告だけを出す。

- 語は、半角と全角の空白で区切る。全体で200文字以内、10語までとする。
- 英字の大文字と小文字は区別しない。
- 対象は本文の全体で、題名だけに限らない。
- 一覧の絞り込みと重ねて使える。
- 入力から0.3秒後に検索する。日本語の変換中は、確定してから検索する。
- 一覧を読み直したときは、同じ語で検索をやり直す。報告を送信したときは、受付した報告が一覧に出るように、検索語を消す。
- 検索できなかったときは、絞り込みを外した一覧を出し、理由を示す。

要求と応答は[API仕様](bug-reporting-api.md#本文の検索)に従う。

## 修正後の確認

対応状況は、受付済み → 対応中 → 修正済み・公開待ち → テスター確認待ち → 確認完了の順に扱う。
確認対象の版は[APIの必須項目](bug-reporting-api.md#対応状況と確認)に従って指定する。
対応状況の更新はGitHubのIssueへ書き込まない。

報告の詳細は、次の操作のボタンを、1行の帯で示す。案内の文は出さず、ボタンの名前で、次の操作を示す。操作がなく、確認対象のバージョンや連絡もない報告（確認完了など）には、帯を出さない。帯は、詳細をスクロールしても、詳細の上に残る。入力欄を開いている間は、画面の高さが足りなくなることがあるため、帯を固定せず、詳細と一緒にスクロールする。

- 受付済みと対応中は、帯のボタン1回で、次の段階へ進める。開発側の連絡や確認してほしいバージョンを添えるときは、「入力して進める」で、帯の下に入力欄を開く。
- 修正済みから確認待ちへ進めるときは、確認してほしいバージョンが要るため、ボタンで入力欄を開き、入力してから送る。
- テスターの確認結果は、バージョンと結果が要るため、ボタンで入力欄を開き、入力してから送る。

確認結果には、実際に確認した版と「直った」「まだ起きる」を保存する。対象版で直った場合は確認完了、対象版でまだ起きる場合は対応中へ戻す。違う版での確認は履歴に残し、対応状況を変えない。

対応状況と確認履歴は同じトランザクションで保存する。更新番号と再送の扱いは[APIの条件](bug-reporting-api.md#対応状況と確認)に従う。GitHub取得の失敗でも保存済みの確認結果を保持する。

## 初期設定

実行環境は[READMEの起動手順](../README.md#起動と検証)に従う。保存先を初期化して起動する。

```powershell
npm run bug:init
npm start
```

初期化は既存のDBを上書きしない。既存の保存先を使う場合は再初期化せず、サーバーを起動する。ポートは[起動と検証](../README.md#起動と検証)に従って指定する。ブラウザでは起動したポートの `/bugs/` を開く。

GitHubを使う場合は、運用者が選んだrepositoryを設定して再起動する。次の値は形式の例で、実在の報告用接続先を示さない。

```powershell
$env:BUG_REPORTING_GITHUB_REPO = 'example/bug-reports'
npm start
```

容量と件数は次の管理コマンドで変更する。既存の添付は保持する。

```powershell
npm run bug:settings -- set-policy --max-bytes <合計容量のバイト数> --max-files <ファイル数>
```

## 人のテスターとAIの操作

人のテスターは「バグを報告」から本文、任意の版、任意のカテゴリ、再現データを送る。受付結果の報告を開き、本文と添付を確認する。受付後は詳細から再現データを追加する。

報告フォームは保存失敗と同じページ内での開き直しに対して入力を保持する。再読み込みでは未保存の本文を失う。確定した未登録データはサーバーから再取得して選び直せる。送信の応答が途切れた場合は、保存結果を確認してから再試行する。

CodexとClaudeなどのAIは[API仕様](bug-reporting-api.md)に従い、再送時は同じ受付キーを使う。別の実行環境から使うには、このPCのサーバーへ接続できることが必要となる。

### まとめを1件ずつに分けて登録する

文章（番号や箇条書き）やチャットのスレッドで届いた、複数の不具合のまとめを、AIが1件ずつに分ける。運用者が確認してから、AIがAPIで登録する。分割の画面は設けない。

報告は実在の内容になる。このリポジトリのIssue、PR、文書には貼らず、AIとの会話の中だけで扱う。登録したGitHubのIssueはツールから削除できないため、運用者の確認の前には登録しない。

1. 運用者が、まとめをAIに渡す。AIが接続するサーバーのURLも伝える。
2. AIが、[分け方の規則](#分け方の規則)に従って1件ずつに分け、件ごとに、題名、本文、既出の候補を一覧にして示す。
3. AIが、件ごとに、本文の検索（`POST reports/search`）で既出の報告を探し、候補の題名を示す。
   - 検索語は、題名から固有の語を1〜3語選び、空白で区切る。語を足すほど、すべてを含む報告だけに絞られるため、見落としが増える。
   - 見つからないときは、語を減らすか、言い換えて、もう一度探す。字面が違う報告は見つからない。
4. 運用者が、登録する件、登録しない件、まとめる件、分け直す件を決める。
   - 登録先のrepositoryと公開範囲も確認する。公開repositoryへ登録した報告文は、第三者も読める（[GitHub登録](#github登録)）。
5. AIが、選ばれた件を、`POST reports` で1件ずつ登録する。次の件は、応答を確認してから登録する。
   - 受付キーは、まとめと件ごとに固定した値にする。例：`bundle-20261012-a2`
   - 同じ件を再送するときは、同じ受付キーと同じ内容で送る。同じ報告が返り、重複しない。内容を変えると409になる。
   - 応答が途切れたときは、`GET reports` で受付済みかを確かめてから再送する。
   - 失敗した件は、そこで止めて、運用者に示す。
6. AIが、登録した件の受付IDと題名を示す。GitHubへの登録は少し遅れるため、数秒後に `GET reports/:reportId` でIssue番号を読み取って示す。登録中や失敗の報告は、そう示す。

#### 分け方の規則

- 1つの不具合を1件にする。1つの投稿に複数の不具合があれば分け、同じ不具合についての複数の投稿は、1件にまとめる。
- 本文は、元の文章を一字も変えずに残す。外してよいのは、番号や箇条書きの記号と、スレッドの投稿者名と日時だけである。スレッドでは、同じ不具合の投稿を、投稿の順に並べる。投稿者名と日時は、運用者が求めたときだけ、本文に含める。
- 報告の先頭行が題名になる。先頭が前置き（「別件です」「これは不具合ではないかもしれませんが」）や質問（「私だけ？」）で、題名にならないときは、短い題名の行を先頭に足す。足した行は、示す一覧で分かるようにする。
- お礼、相づち、雑談の投稿は、登録しない候補として、理由を添えて示す。
- 1件か複数かの判断や、不具合かどうかの判断に迷うときは、決めずに、候補を並べて運用者に聞く。
- 要望や仕様の質問も、今のツールは不具合の報告と区別できない。登録するかは、運用者が決める。

## バックアップ

サーバーと管理コマンドを停止してから、保存先フォルダー全体をコピーする。DBと添付を別々の時点でコピーしない。復元は別の保存先へ行い、元の保存先を保持したまま報告と添付を確認する。

## 実装状況と未確認事項
