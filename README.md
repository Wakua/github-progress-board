# github-progress-board

複数プロジェクトを登録し、次の作業・要対応・確認待ちを把握する進捗管理ツール。プロジェクトを選ぶと、目標・作業・依存関係・成果の根拠を確認、編集できる。手動入力と読み取り専用のGitHub snapshotを分けて保持する。`npm start`のローカルモードは同じブラウザに保存する。認証付きのクラウド共有保存も持つ（[クラウド共有保存](#クラウド共有保存の実装と確認範囲)）。

初回は空の一覧を表示する。複数のプロジェクトを名前とrepository URLで登録できる。手動計画の進捗、Issue、担当者、見積、期限は自動で補わない。ローカル起動時は、設定で指定したrepository（[ローカルのghで自動取得する](#ローカルのghで自動取得する)）からGitHubの目標・作業・期間・リリースとIssue・PRの状態を別領域へ自動取得できる。集計テスト用の架空データは、通常画面には読み込まない。

## 画面の構成

画面は、人が知りたい問いごとに分ける。規則は各節に書き、ここでは問いと節の対応だけを示す。

| 画面 | 答える問い | 仕様 |
| --- | --- | --- |
| 全体一覧 | どのプロジェクトで、次に何をするか・人の手が要るか | [プロジェクトと保存](#採用済み仕様プロジェクトと保存ローカルモード)の先頭 |
| 承認待ちのPR（プロジェクトの上部） | 人の承認が上限に達していないか | [承認待ちのPR](#承認待ちのpr) |
| ① 自分の作業（タブ） | 今日何をやるか | [自分の作業と要対応](#自分の作業と要対応)。GitHubで計画しているプロジェクトは[GitHubから表示する計画](#githubから表示する計画) |
| ② イテレーション（タブ） | 期間内に間に合うか | [イテレーションと期限](#イテレーションと期限)、[担当別の負荷](#担当別の負荷)、[表示ルール](#表示ルール) |
| 詳細（右のパネル） | なぜ止まっているか、何が終われば進むか | [操作](#操作)、[詳細での入力と移動](#詳細での入力と移動) |
| ③ 要対応（タブ） | どこで人の手が要るか | [要対応タブ](#要対応タブ試作)（試作）。行動の整理は[③④の行動の整理](docs/attention-release-behavior.md) |
| ④ リリース（タブ） | リリースに間に合うか | [リリースタブ](#リリースタブ試作)（試作）。行動の整理は同上 |

GitHubで計画しているプロジェクトはGitHubの作業を表示し、手動の計画はGitHubのないプロジェクトに使う（2026-10-04 ユーザー決定）。

## クラウド共有保存の実装と確認範囲

既存の画面をWorkerに載せ、同じSites認証ユーザーのデータをD1の`DB` bindingに保存する構造を追加した。全プロジェクトの所属と参照を検証し、サーバーの保存確認後に画面を更新する。古い端末の上書き、アカウント変更、通信失敗、破損では編集を停止し、変更候補と未保存入力を退避できる。初回は空であり、既存ブラウザ保存やサンプル記録を自動投入しない。

既存データの移行は、移行元のバックアップ保存、project ID・repository URLのpreview、明示確認を経て新規プロジェクトを追加する。同一IDの異なる内容は全件拒否し、原本や既存のクラウド計画を上書きしない。表示中のプロジェクトだけは端末ごとの設定として保持する。

`npm run build`はクラウド用の`dist/client`と`dist/server`を生成する。実行時依存は追加せず、ビルド・schema生成用の開発依存を3件に限定した。`npm run preview:cloud`はloopback専用の隔離QAであり、実際のSites認証やD1を利用しない。

クラウドでは、[用意済み記録の初回取込](docs/prepared-workspace.md)、[仮見積の登録](docs/estimate-proposals.md)、[本人限定MCP](docs/sites-mcp.md)を使う。作業行には[完了条件達成率](docs/progress-visibility.md)を表示する。これらは明示操作で保存し、同梱のサンプル記録や進捗案を自動投入しない。

検証はGitHubソースと隔離QAについての確認である。本番の認証、永続D1、実端末共有、公開Site全体との一致は未確認である。公開前の条件は[反映前の検証](docs/cloud-release-verification.md)を参照する。

- 操作・保存範囲・安全性・公開準備：[docs/cloud-workspace.md](docs/cloud-workspace.md)
- 用意済み記録の取込用JSON（架空のサンプル）：[samples/prepared-workspace.json](samples/prepared-workspace.json)

## 採用済み仕様：プロジェクトと保存（ローカルモード）

- 全体一覧はプロジェクトごとの次の作業・要対応・確認待ち・承認待ちのPRに絞る。次の作業には作業中の仕事を優先し、なければ今の期間、先の期間の順に着手可能な仕事を表示する。要対応と前提待ちの作業は次の作業に選ばない。要対応・作業中・前提待ちの定義は[自分の作業と要対応](#自分の作業と要対応)に従う。複数の候補や全作業は選択したプロジェクトで確認する。
- プロジェクトは変更されないID、名前、repository URL、専用のデータを持つ。目標、親子Issue、作業、イテレーション、判断、変更記録にprojectIdを持たせる。作業の依存と成果の根拠もそのプロジェクト内に保持する。
- 内部参照はプロジェクトIDとその中のエンティティIDで行う。Issue番号は参照キーにしない。同じ番号を別プロジェクトで登録でき、詳細にはrepository名と番号を併記する。同一プロジェクト内のIssue番号の重複や、別プロジェクトへの参照、循環する依存を保存しない。
- repository URLは任意で、GitHubのrepository URLを受け付ける。未登録はnullのまま保持する。credentialを含むURLは受け付けない。ローカル起動時に設定したrepositoryだけは、登録後にsnapshotを自動取得する。
- 新しい目標のIssue状態は未確認、新しい作業の状態は未確認または明示した未着手とする。Estimate、担当者、期限、Issue番号は不明ならnull、完了条件と証拠は入力するまで空のまま保持する。
- 選択したプロジェクトと全データを、バージョン付きの一つのJSONとしてlocalStorageへ保存する。変更候補を複製して構造・所属・参照を検証し、保存に成功してから画面に反映する。保存容量不足や例外で失敗した変更は反映しない。
- 直前の有効な保存をバックアップに保持する。主データが破損した場合は、有効なバックアップの閲覧に切り替え、編集を停止する。無効なバックアップは読み込まない。未対応バージョンや主データの欠落も自動で空のデータへ上書きしない。
- 復旧は画面で明示的に行う。バックアップまたは検証済みの復旧用JSONを読み込み、破損した主データを復旧用領域に退避してから置き換える。以前の破損原本がすでに別内容で残っていれば復旧を停止する。「保存データを退避」で主データ・バックアップ・破損原本を文字列のまま書き出せる。
- 別タブから変更された場合は編集を停止する。再読み込み後に編集を再開する。Web Locksを利用できるブラウザでは保存を直列化し、保存直前にも古いタブの上書きを検出する。Web Locksを利用できない環境では変更検出のみで、同時書込の完全な排他は保証しない。

**保存の範囲は同じブラウザの同じオリジン（scheme・host・port）である。** 手動計画のサーバー保存、別ブラウザ・別端末との共有、GitHubへの書き込みは行わない。private browsingの終了やブラウザデータの削除で失われる。必要なデータは「データを書き出す」で退避する。HTTPの127.0.0.1:4319と、別ポートや別ホストの保存領域は共有されない。

## データ構造とsnapshot

`dist/workspace.mjs`が登録、projectIdによる境界、検証、保存を担当し、`dist/engine.mjs`は一つのプロジェクトの表示判断と集計を担当する。UIは表示対象のプロジェクトを明示して変更候補を作る。プロジェクト間を切り替えると詳細と展開状態を閉じ、前の画面からの編集を持ち越さない。

保存キーは`progress-tool.workspace.v1`、直前バックアップは`.backup`、破損原本の退避は`.recovery`である。最上位は`schemaVersion`、`selectedProjectId`、`projects`を持つ。各projectは`id`、`name`、`repositoryUrl`、`data`を持ち、dataの目標・作業等は既存の集計処理で扱える形を維持する。Issueの出典識別にはprojectId、repository URL、entityId、Issue番号の組を使う。

各projectは任意の`githubSnapshot`を持つ。`data`は手動計画、`githubSnapshot`はGitHubの状態であり、取込時に変換・統合しない。既存v1データは移行せず読み込める。snapshotにはprojectId、repository URL、取得日時、全ページの取得元URL、Issue/PRの種類・番号・URL・タイトル・状態・GitHub更新日時を保持する。PRにはDraft・merge日時も保持する。識別はrepository URL（大文字小文字を同一視）・種類・番号の組で行う。

`dist/github-snapshot.mjs`が検証・REST adapter・古さの表示を担当する。Issue/PRのOpen・Closed・Merged・Draftを表示するが、手動の作業状態、完了条件、受入完了へ写さない。Issue・PRの基本項目の見積・期限はnullを保持する。任意の`planning`に親子Issue、Milestone、Projectの「担当」「Iteration」「Estimate」「Status」と、Issueの依存関係（blocked by）・紐づく開いたPR・`仕様` ラベルを保持する。`dist/github-planning.mjs`が検証と集計、`dist/github-planning-view.mjs`が読み取り専用表示を担当する。planningを含まない既存snapshotも読み込める。Issue本文、コメント、CI、レビュー、完了条件は取得しない。

## 採用済み仕様：読み取り専用GitHub snapshot

- 「GitHub snapshotを読み込む」からJSONを読み込み、repositoryごとに取込先を確認して保存する。同じrepositoryの既存プロジェクトを選ぶか、新しい空のプロジェクトを登録する。URL未登録の手動プロジェクトや別repositoryのプロジェクトへ自動結合しない。同じrepositoryが複数登録されていれば取込先の選択を必須とする。
- 「サンプルの3repositoryを確認」で、同梱の架空のsnapshot（`dist/github-snapshot.json`）をpreviewできる。初回には自動取込・自動保存しない。Issue/PRはそれぞれレシピアプリ 10/8件、予約管理アプリ 12/14件、本ツール 0/2件である。実在のrepositoryの状態ではない。
- GitHubがsnapshotの正本である。snapshot詳細は読み取り専用とし、手動の目標・作業・証拠・完了条件・担当・見積・期限を変更しない。全体一覧は手動計画の次の作業・要対応・確認待ちと、snapshotの承認待ちのPRの件数を表示する。その他のGitHub状態は選択したプロジェクトで確認する。
- PRのMergedと作業の受入完了、IssueのClosedと完了条件の達成を区別する。受入完了は未確認として表示する。計画情報の表示は[GitHubから表示する計画](#githubから表示する計画)に従う。PRだけから進捗率・次の作業・要対応を推定しない。
- 一覧と詳細に取得時刻・経過時間を表示し、24時間以上経過したsnapshotを「古いsnapshot」と表示する。表示中も1分ごとに経過時間だけ更新する。古いsnapshotは閲覧できるが、現在保存しているものと同じ取得日時・より古い取得日時で上書きしない。各Issue/PRの更新日時が巻き戻る更新も拒否する。
- repository・projectId・種類・番号・出典URL・日時・状態・schema・重複・全ページ取得の申告を検証する。未知項目やschema、5MiB超、5分を超える未来の取得日時、不整合な日時、部分取得は拒否する。JSONの構造・整合性検証はGitHub由来の真正性を保証しないため、許可済み接続または既存の認証済み取得経路から作ったJSONを使う。
- 複数repositoryの取込を一回の保存で処理する。一件の検証失敗、容量不足、別タブ更新では全件を反映せず、保存済みの手動データとsnapshotを保持する。保存済みsnapshotの破損は既存の復旧機構で検出し、主データを上書きせず編集・取込を停止する。

## ローカルのghで自動取得する

既存の認証済み`gh`とNodeが同じ環境にある場合、次の起動後に`http://127.0.0.1:4319`を開く。新しいcredential、ログイン、npm依存を追加しない。

```sh
npm start
```

自動取得するrepositoryは、環境変数 `PROGRESS_GITHUB_REPOS` にカンマ区切りで指定する。`owner/repository` と `https://github.com/owner/repository` のどちらでもよく、50件までとする。既定は空で、指定がなければ自動取得しない。

```sh
PROGRESS_GITHUB_REPOS=owner/repo-a,owner/repo-b npm start
```

```powershell
# PowerShell
$env:PROGRESS_GITHUB_REPOS = 'owner/repo-a,owner/repo-b'; npm start
```

指定したrepositoryのURLをプロジェクトに登録すると、JSONファイルを扱わずGitHub snapshotを自動保存する。初回の空一覧からは取得・登録しない。ブラウザは起動時にサーバーから許可された一覧を受け取り、それ以外のrepositoryを要求しない。

ページ起動時、新しい対象プロジェクトの登録後、表示中の5分ごとに取得する。非表示のタブは新しい取得を始めず、再表示時に前回から5分以上経っていれば取得する。選択したプロジェクトの両タブと「登録・取込」に取得状態と「GitHubを再取得」を表示する。「自分の作業」ではGitHubの作業を分類して表示し、手動計画は畳む。再取得は設定したrepositoryのうち登録済みのものを順に取得する。他のrepositoryはJSONの手動取込を使う。同じrepositoryを複数登録した場合は、そのrepositoryの各projectIdへsnapshotだけを反映し、手動計画はそれぞれ保持する。

Nodeがブラウザ外で`gh api --hostname github.com`を呼ぶ。Issue・PR・MilestoneはREST GETで、親子IssueとProjectはGraphQL queryで読み取る。ブラウザからcredential・コマンド・queryを渡さず、GitHubへの書き込みを行わない。各一覧を最後のページまで取得し、`buildSnapshot`・`attachSnapshot`で検証する。RESTとGraphQLのIssue集合・更新日時が一致しない場合も更新を見送る。取得はGitHub側の一時点のトランザクションではなく、取得中の変更をすべて検出する保証はない。完了条件の取得は別の作業とする。

取得は同時に1repositoryまでとし、同repositoryの同時要求を共有する。取得中に届いた登録後の取得要求と明示的な再取得要求はまとめて保持し、現在の取得が終わった後に最新の登録先を確認して処理する。要求が届いた後に取得を始めて保存したrepositoryは取り直さない。成功結果はNodeのメモリで15秒だけ再利用し、取得全体90秒・gh一回20秒・生応答の合計20MiB・snapshot 5MiB・各一覧最大50ページの上限を持つ。GraphQLのIssueは1ページ100件で取得する。IssueごとのProject登録は20件、Project登録ごとのフィールド値は100件、前提（blocked by）は50件、前提ごとのラベルは50件、紐づくPRは20件までとし、次ページが残る場合は不完全として更新を見送る。途中失敗、ページ不整合、古い取得日時、保存容量不足では保存済みのsnapshotと手動計画を保持する。同じ取得日時・同じ内容の共有応答は保存を省略する。

手動編集は取得中も使える。保存直前に最新の手動計画を読み直し、既存のWeb Locksと保存検証を使う。詳細drawerと未保存の入力を更新で閉じない。開いている「登録・取込」のsnapshot一覧とGitHub詳細は最新snapshotのタイトル・状態・日時で更新する。対象が最新snapshotに含まれなくなった場合は、その旨を詳細に表示する。別タブが保存した場合は取得結果も反映を止め、再読み込みを案内する。自動保存も別タブの編集停止を起こすため、編集は一つのタブで行う。

サーバーは127.0.0.1だけで待ち受ける。APIはloopback Host、同一Origin、プロセスごとのCSRF token、設定したrepository、入力サイズを検証し、CORSを許可しない。ghのstderr・credentialをブラウザに返さない。Nodeのキャッシュは保存先ではなく、サーバー再起動で消える。最終的な保存先は同ブラウザ・同オリジンのlocalStorageである。hosted SiteのMCP経路・サーバー保存・双方向同期・deployはこのローカル機能の範囲に含めない。

ポートの指定方法は[起動と検証](#起動と検証)に従う。

## GitHubから表示する計画

- 子Issueを持つ最上位の親Issueを目標とし、子Issueを持たないIssueを作業として表示する。集約用の親Issueは作業件数へ加算しない。親を持たない単独Issueも作業に含め、親が別repositoryの場合は目標を推定しない。参照できない子Issueがある集約用Issueは、その不足を詳細に表示する。
- 「自分の作業」はProjectの「担当」で絞り、GitHubの作業を[自分の作業と要対応](#自分の作業と要対応)と同じまとまりに分ける。
  - 要対応：Project未登録・Status未設定・Statusが Todo/In Progress/Done 以外・Projectごとに異なる、`仕様` ラベル付きで開いている（仕様待ち）、Iterationの最終日が過ぎた、開いた前提のIterationの最終日が過ぎた、In Progress なのに担当がいない、In Progress なのに開いた前提がある。
  - 確認待ち：紐づく開いたPRがReady（承認待ちのPR）。作業中：Status が In Progress（Draft PRがあれば理由に示す）。前提待ち：開いた前提（blocked by）がある。着手可能：それ以外の Todo。Closed と Done は「完了・Closed」に畳み、受入完了へ変換しない。
  - 前提はIssueの依存関係（blocked by）を使い、別のrepositoryのIssueでもよい。決まっていない仕様は「〇〇の仕様を決める」Issueに `仕様` ラベルを付けて担当を決める人にし、止まっているIssueをそれに blocked by でつなぐ。仕様のIssueは仕様書と同じrepositoryに置き、仕様書に書けたら閉じる。前提が仕様のIssueなら理由を「仕様待ち」と示す。今の期間はProjectごとに決め、作業のどれかのProjectで今の期間なら「着手可能（今の期間）」に入れる。複数Projectに登録した作業は、どれかのProjectのIterationが終わっていれば期限超過とする。同じrepositoryの前提は、子Issueを持つ親Issueでも期限超過を判定する。別のrepositoryの前提は開閉と `仕様` ラベルだけを読み、ProjectのIterationは取得しない。そのため、別のrepositoryの前提の期限超過は要対応に入れない。
  - 判断以外の待ちの理由は扱わない。前提・紐づくPR・仕様ラベルを持たない旧snapshotは、その旨を示して残りの条件で分ける。
- モジュールはIssueの「module:<モジュール名>」ラベルで分類する。作業から親へたどり、最も近いIssueのモジュールラベルを使う。親が別repositoryの場合は継承しない。複数のモジュールラベルがある作業は、それぞれのモジュールに含める。repository全体はIssueごとに一度だけ集計し、モジュール間の件数は合算しない。該当ラベルがなければ「モジュール未分類」、ラベル情報を持たない旧snapshotは「モジュール情報未取得」と表示する。
- モジュールごとに、その範囲の目標・リリース・作業を表示する。目標やMilestoneが複数モジュールにまたがる場合は、そのモジュールの作業だけを集計する。
- GitHubの終了率は、取得したrepository内の見積設定済みの末端Issueを対象に、ClosedのEstimate合計を集計対象のEstimate合計で割り、整数に丸める。集計対象に未終了がある間は最大99%とする。親Issueは加算しない。横棒と残りのEstimateを表示し、受入完了との区別は[読み取り専用GitHub snapshot](#採用済み仕様読み取り専用github-snapshot)に従う。
- Estimateが未設定またはゼロの作業は、終了率と残りの作業量の集計から除外し、除外件数を表示する。作業件数・Open/Closedの内訳・作業一覧には残す。集計対象がない範囲は「見積のある作業なし」と表示する。複数Projectによって見積の出典が確定しない範囲は終了率を表示せず、出典確認の件数を示す。
- 「イテレーションから確認」を開くと、Projectごとの期間、目標、作業を確認できる。期間内の終了率はそのProjectのEstimateだけで集計する。再取得でも担当の絞り込みと一覧の開閉を保持する。
- Milestoneはリリースとして、名称・期日・割り当てた作業のOpen・Closedと内訳を表示する。Milestoneを目標へ変換せず、期日から達成見込みを推定しない。
- 複数Projectに登録したIssueは、各Projectの担当・Status・Estimate・Iterationを保持する。期間の集計はそのProjectの割当だけを使い、詳細で各出典を確認できる。
- 計画情報を含まないsnapshotは「未取得」、取得したProjectの空欄は「未設定」、Project登録がないIssueは「Project未登録」と表示する。取得失敗では直前のsnapshotと手動計画を保持する。

## snapshot JSONを手動で再取得する

ブラウザからGitHubへ直接アクセスせず、取得と取込を分ける。新しい認証情報、ログイン、OAuthは作らない。既存の`gh`に対象repositoryの読み取り許可がある環境では、次のGET専用helperで新しいファイルを作る。

```sh
node scripts/fetch-github-snapshot.mjs --repo owner/repo --output snapshot-new.json
```

helperはIssue/PRの`state=all`を100件ずつ取得し、最後の100件未満のページまで進む。取得上限・欠落・重複・Issue一覧とPR一覧の不一致があれば出力しない。既存の出力ファイルは上書きせず、失敗時も保持する。取得は複数GETでありGitHub側の一時点のトランザクションではない。取得中の変更をすべて検出する保証はない。

`gh`を使えない環境では、別の方法で取得した生のREST配列を次の形で保存すれば、追加のネットワークアクセスなしで同じhelperを使える。

```json
{
  "repositoryUrl": "https://github.com/owner/repo",
  "fetchedAt": "2026-10-03T16:14:45Z",
  "issuePages": [[]],
  "pullPages": [[]]
}
```

`issuePages`はPRも含むGitHubのIssue一覧、`pullPages`はPR一覧のREST応答をページ順に格納する。上記の空配列は形式説明であり実データではない。取得日時を実際のGET完了後に記録し、取得していないページや日時を補わない。

```sh
node scripts/fetch-github-snapshot.mjs --repo owner/repo --from-pages pages.json --output snapshot-new.json
```

単一snapshotをそのまま読み込める。複数を一度に読み込む場合は`{"type":"github-snapshot-bundle","schemaVersion":1,"snapshots":[...]}`で包む。取込用JSONにprojectIdは含めず、画面で取込先を決める。`npm start`のローカルモードでは更新も同ブラウザ・同オリジンに保存する。クラウドモードでは同じsnapshotを共有workspaceに保存する。ローカルモードで設定したrepositoryは上記の自動取得に対応する。クラウドモードはローカルghの自動取得を実行しない。双方向同期は行わない。

## 操作

- 上部の「登録・取込」で登録操作と選択したプロジェクトのGitHub snapshotを開く。「プロジェクトを登録」で名前と任意のrepository URLを入力し、「GitHub snapshotを読み込む」で取込を開始する。
- 上部の選択欄または全体一覧の「プロジェクトを開く」で表示を切り替える。再読み込み後も選択を復元する。
- プロジェクトを選び、「登録・取込」の「目標を登録」「作業を登録」で自分のデータを追加する。登録・取込の操作とGitHub snapshotの欄は、普段の作業一覧には表示しない。ここから開いた登録・取込の操作は、保存後に「登録・取込」へ戻る。登録フォームとsnapshotのIssue・PR詳細からは、詳細の上部にある「登録・取込へ戻る」で元のパネルを開く。登録フォームの未保存入力は、戻ってから開き直しても保持する。
- 作業の「前提作業」で同じプロジェクトの作業を複数選択し、依存を保存する。未選択で前提なしにできる。
- 作業の「完了条件の編集」で条件を追加、変更できる。同じ文の確認状態を保持し、新しい条件は未確認にする。条件未登録の作業は完了として保存しない。
- 未確認の作業は「未着手として確認」を押してから開始する。

- 選択したプロジェクトの「自分の作業」「イテレーション」のタブで画面を切り替える。左右の矢印キーでも切り替えられる。選んだタブはブラウザに記憶する。
- 「自分の作業」の担当者のボタンで、全員・各担当者・未担当に絞り込む。選択はプロジェクトごとにブラウザに記憶する。件数だけを示すまとまりは、見出しを押すと展開する。
- 「Issueツリー」で、すべての親子Issueのツリーを開く。
- 目標の見出しにある「目標全体」で、期間をまたぐ進捗と、対象の親Issueのツリー・優先順・変更記録を開く。
- 子Issueを持つ行を押すと、その下のIssueを展開する。「内訳を確認」で、対象Issueの進捗と配下の作業を開く。
- 作業の詳細にある階層表示から、上位のIssueへ戻る。
- 一覧の作業名で、成果の根拠・完了条件・状態・待ちを開く。
- 作業の詳細にある「理由・前提を確認」で、着手・継続の判断と関連する前提・後続作業を確認する。
- 目標全体の詳細にある「依存関係」で、進行を止めている作業と、解除に必要な対応を開く。
- 作業の詳細にある「判断待ちの登録」で、判断の名前・選択肢・判断材料・判断する人を入力して判断待ちを登録する。
- 判断待ちを解除するときは、採用する内容と理由を記録する。
- 作業の詳細にある「Estimate（ポイント）」で、保存するEstimateを変更する。空欄で更新すると未入力に戻す。
- イテレーションの行を押すと、担当別の負荷と対象作業の一覧をその下に開く。複数の期間を同時に展開できる。「すべて展開」で全期間の作業を並べ、「すべて閉じる」で集計だけに戻す。
- イテレーション内の目標の見出しで、その目標の作業行を展開・折りたたみする。「待ちの理由」の名前で、作業の前提と待ちの理由を開く。
- 「担当別の残り」で担当者名とポイントのボタンを押すと、その担当者の未完了作業を状態別にまとめた担当別一覧を開く。
- 担当別一覧から作業や前提を開いたあとは、詳細の上部にある「担当別一覧へ戻る」で元の一覧を開く。
- 作業の詳細にある「担当者」で、保存する担当者名を変更する。空欄で更新すると未担当にする。
- 親Issueのツリーにある「期間の内訳」で、その目標だけのイテレーション一覧を開く。
- 「期限超過 N件」で、終了したイテレーションに残る未完了の作業をまとめて確認する。
- 作業の詳細にある「イテレーションの割当」で、保存する割当を変更する。未割当も選べる。

## 承認待ちのPR

人とClaude・Codexが並行して作業すると、PRの承認が人に集まる。担当者は作業中のPRをDraftにし、作業を終えて承認を求めるときにReadyにする。開いているReadyのPRを「承認待ちのPR」とし、上限を2件とする。Draftは担当者が作業中であり、承認待ちに数えない。上限に達している間、AIは新しくPRをReadyにしない（AGENTS.md）。

選択したプロジェクトの画面では、タブの上に承認待ちのPRの件数・上限・一覧と、上限に達しているかを表示する。一覧はPR番号の順に並べ、番号からGitHubのPRを開く。件数はGitHub snapshotから求めるため、取得時刻を示し、古いsnapshotでは件数が最新でない可能性を示す。snapshotが未取得なら未取得と表示する。全体一覧のカードにも件数と上限の状態を表示する。

## 自分の作業と要対応

「自分の作業」は、選択したプロジェクトの未完了の作業を、次に手を付ける順のまとまりで並べる。作業は人とAI（Claude・Codex）が並行して行うことを前提とする。

未完了の作業は、要対応 → 確認待ち → 作業中 → 前提待ち → 着手可能 の順に判定し、最初に当たったまとまりに一つだけ入れる。

| まとまり | 対象 |
| --- | --- |
| 要対応 | 人が手を入れないと進まない作業。次のいずれかに当たる：状態が未確認、待ちの理由がある、未解決の判断待ちがある、作業自身のイテレーションが終了している、未完了の前提のイテレーションが終了している、作業中なのに担当者がいない、作業中なのに未完了の前提がある |
| 確認待ち | 状態が確認待ち |
| 作業中 | 状態が作業中 |
| 前提待ち | 状態が未着手で、未完了の前提がある |
| 着手可能 | 状態が未着手で、未完了の前提がない |

表示は 作業中 → 要対応 → 確認待ち → 着手可能（今の期間）→ 着手可能（先の期間・未割当・期間不明）→ 前提待ち の順に並べる。最後の2つは件数だけを示し、見出しで展開する。件数が0のまとまりは見出しも表示しない。今の期間は進行中のイテレーションとし、進行中がなければ次に始まるイテレーションとする。

各行には作業名、担当者、期限、理由を表示する。要対応の行は当たった条件をすべて理由として示し、状態も表示する。前提待ちの行は先頭の前提と残りの件数を示す。完了条件、成果の根拠、Estimate、目標全体の進捗は詳細で確認する。

GitHubで計画しているプロジェクトは、GitHubの作業を同じまとまりで並べ（[GitHubから表示する計画](#githubから表示する計画)）、手動の作業は畳んで件数だけを示す。担当者の絞り込みもGitHubの「担当」の1組を表示する。

担当者の絞り込みは、ログインした本人の判定ではなく表示の絞り込みである。選択肢は未完了の作業に登録された担当者名から作り、担当者のいない作業があれば「未担当」も加える。

仕様などが決まらず進められない作業には、判断待ちを登録する。登録すると、同じ目標・親・イテレーションに判断作業を作り、元の作業の前提に置く。判断作業の担当者が判断する人であり、判断する人の絞り込みでは要対応（判断待ち）、元の作業の担当者の絞り込みでは前提待ちに入る。判断が済むまで元の作業は進められないため、作業中・確認待ちの元の作業は未着手に戻す。状態が未確認の元の作業は未確認のまま残り、要対応に入る。判断作業の完了条件は「採用する内容と理由を記録する」とし、判断を記録すると判断作業が完了して元の作業の前提が解ける。選択肢は2件以上で重複させない。判断作業のEstimateは任意で、未入力なら未入力として集計する。

## 要対応タブ（試作）

人が手を入れるものを、一つの一覧に並べる（[ユースケース](docs/use-cases.md)の場面1）。各行は、作業名と短い理由（期限切れ、担当なし、仕様待ち、など）だけである。手動の計画もGitHubの計画も同じ形である。

- 並びは、承認待ちのPR（→ 承認）、要対応（期限切れの古い順）、「あなた」の担当の順。
- 何をするかは書かない。解除は、手動の計画ではツール内、GitHubの計画ではGitHub上（読み取り専用。「GitHubを再取得」で反映）で行う（[③④の行動の整理](docs/attention-release-behavior.md)の表）。
- 「あなた」は、担当者名を選ぶ。選んだ名前はプロジェクトごとにブラウザへ記憶する。
- 前提待ちは含めない。タブ名の数字は、一覧の件数である。
- 確認していない操作：幅の狭い画面、複数のProjectに登録したIssueの表示。PRとIssueの対応は、PRが `Closes #番号` の場合だけ分かる。

## リリースタブ（試作）

Milestoneごとに、計画のはみ出しだけを示す（[ユースケース](docs/use-cases.md)の場面2）。GitHubで計画しているプロジェクトだけに出す。完了予定日と、間に合うかの判定は出さない。

- 見出しに、期日、期日までの残りの期間数、残りのEstimateを出す。
- 一覧に出すのは、期日より後に割り当てた作業（割当の期間が期日をまたいで終わるものを含む）、未割当の作業、見積なしの作業（理由つき）。
- 「要対応 N件（期限切れ M件）→」は、要対応タブへ移る。期限切れは、作業自身と前提の期限超過の両方を数え、作業名は出さない。
- 「最長の流れ」は、前提でつながる作業のうち、Estimateの合計が最大のもの。別のMilestoneにある未完了の前提もたどる（リリースを止めるため）。各作業は詳細を開くボタンで、見積のない作業は足さず、件数を添える。
- 期日のない・閉じたMilestoneは出さない。
- 実装：`dist/release.mjs`。変更前後の画面は `docs/screens/6/` にある。
- 確認していない操作：幅の狭い画面、複数のProjectに登録したIssueの表示。

## 親子Issue

目標を表す親Issueは、イテレーション内の目標グループに対応する。子Issueを持つIssueは作業を集約し、さらに下の階層も詳細ツリーで表示する。実際の作業と完了条件を持つ最下位のIssueを作業Issueと呼ぶ。親の直下に作業Issueを置く構造にも対応する。

親子関係は仕事の内訳を表す。依存関係は着手の前提を表し、子Issueという理由だけで別の子Issueの完了を待たせない。

集約用のIssueのOpen／Closedと、配下の作業の完了率は分けて表示する。子Issueの完了によって親IssueのOpen／Closedは変更しない。集約用のIssueがClosedでも、配下に未完了の作業Issueがあればその旨を示す。

## 表示ルール

選択したプロジェクトは「自分の作業」タブで開く。「イテレーション」タブは「イテレーション → 目標 → 作業」の一つの階層で表示する。期間をまたぐ目標全体の進捗は右側の詳細に表示する。目標名には短い表示名を使い、正式な目標名は詳細に表示する。短い表示名が未登録の場合は正式な目標名を使う。

説明文、完了した範囲と残る範囲、目標のEstimateの内訳、作業の完了条件の達成率、親子Issueの階層は詳細で確認する。一覧では状態を短いラベル、完了率を数値とバーで表示する。

Estimateは各作業の見積作業量を表し、1ポイントを1日として扱う。0より大きい数値を入力し、0.5などの小数も受け付ける。手動入力をworkspaceに保存する。手動計画の値であり、GitHub snapshotの未取得値とは別に保持する。

親Issueと集約用の子Issueの完了率は、配下の完了した作業IssueのEstimateを配下の全作業IssueのEstimateで割って求める。階層ごとの割合を平均せず、作業Issueを一回ずつ数える。集約用のIssue自身のEstimateは加算しない。作業Issueが未登録の場合は「作業未登録」と表示する。配下に一件でもEstimateが欠けていれば割合を表示せず、未入力の件数を示す。

作業の達成率は、達成した完了条件の件数を全完了条件の件数で割って求め、各条件を同じ重さで数える。完了条件が未登録の場合は、割合を表示しない。目標と作業の割合は小数部分を切り捨てる。未完了の作業が残る目標を100%とは表示しない。Estimateは実際に費やした時間や、残りの暦日数を表さない。

各作業Issueは一つの親を持ち、親子関係をたどった最上位の親Issueに所属する。親Issueは登録順に並べる。  
作業行は状態で間引かず、優先順の変更で作業中の状態を変えない。

前提が完了し、未解消の待ちがない未着手作業を「着手可能」と表示する。  
人間は着手可能な作業を選んで開始する。同じ目標でも別の目標でも複数の作業を並行できる。  
他の目標の作業に依存する場合も、その作業の完了を待つ。

優先順の変更は目標内に適用し、変更理由を記録する。  
後続作業の件数は判断材料として表示する。件数による優先順の自動変更は行わない。

依存関係の詳細では、進行を止めている作業と、直接待っている作業・その先で待っている作業を分けて表示する。対象目標の後続作業に影響する場合は、別の目標の前提も含める。別の前提が残る作業は、その前提も示す。完了した作業を経由するつながりは、待ちとして数えない。

確認待ちは完了として扱わない。  
着手できる作業がない目標では、待ちと未完了の前提を示す。  
すべての作業が完了した目標は達成扱いにする。作業がない目標は達成扱いにしない。

## イテレーションと期限

各作業Issueにイテレーションを割り当て、その終了日を作業の期限として表示する。終了日は、開始日を含む期間の最終日とする。日付と残り日数は日本時間で求め、終了日の当日は「今日まで」と表示する。未完了の作業が終了日を過ぎた場合は、超過した日数を示す。完了した作業には超過表示を付けない。

登録されたすべてのイテレーションを開始日順で縦に並べる。日付が不明な期間は末尾に置く。各行には期間、完了率、残りポイント、期間の状態、作業件数を表示する。完了分と合計のポイントは、目標全体の「期間の内訳」に残す。進行中の期間を強調し、初期表示ではその作業一覧を展開する。進行中の期間がなければ、次に始まる期間を展開する。目標全体の「期間の内訳」では、その目標の作業がある期間を初期展開の候補にする。未割当や割当先が不明な作業は、一覧の末尾にまとめる。

イテレーション内は「目標 → 作業」の順にまとめ、目標名を作業行に繰り返さない。親子Issueの最上位の親Issueを目標として、目標の登録順、目標内の優先順で表示する。期間の中に作業がない目標は表示しない。

目標の見出しには、その期間に属する作業だけの件数、完了率、残りポイントを表示する。作業期限は、未完了の作業が期限を超過している場合に完了率の直後へ表示する。「集計：この期間内」をグループの上に添え、詳細にある目標全体の完了率と区別する。目標ごとに作業行を折りたためる。展開状態は期間・表示箇所・目標ごとに保持し、作業の更新では変えない。

作業行には作業名、担当、状態、Estimate、進行を止めている前提や待ちの理由を表す「待ちの理由」を表示する。待ちの理由は先頭の名前と残件数を示し、詳細で全件を確認する。完了した作業の待ちの理由は表示しない。狭い画面では担当と待ちの理由を作業名の下に置く。中間の親Issueを含む階層は、右側の詳細ツリーで確認する。

期間の集計は、その期間に割り当てた作業Issueだけを対象とする。残りポイントには確認待ちも含める。必要なEstimateが不足している値は未入力として示す。

作業の詳細では、イテレーション未割当なら「期限未設定」、割当先や日付を確認できない場合は「期限未確認」と表示する。該当する作業をまとめた目標の見出しでは、作業期限を「要確認」と表示する。親Issue全体へ一律の期限は付けない。

一覧の展開と割当の変更では、優先順や作業の状態を変更しない。残りポイントと残り日数は判断材料として表示し、期間内に完了できるかを自動判定しない。手動計画のイテレーションと割当はsnapshotから補わない。現在は期間の新規登録UIを持たず、作業の期限は未設定で保持する。

終了したイテレーションに未完了の作業があれば、普段の画面に期限超過の件数を表示する。各期間の行には未完了件数、展開した作業には期限超過の表示を付ける。確認待ちと未確認の状態も対象に含める。未割当や日付が不明な作業は、期限超過と判断しない。

未完了の作業を次の期間へ自動で移さない。人間が成果の確認、待ちの解消、計画の見直しを判断し、継続する期間の割当を変更する。Estimateと完了条件は保持し、変更前後のイテレーションを変更記録に残す。期間の内訳は現在の割当で集計し、変更前の計画に対する達成率の履歴は保持しない。

## 担当別の負荷

各イテレーションの展開部分に、担当者名と未完了作業のEstimate合計を横並びで表示する。幅が足りない場合は折り返す。担当者を選ぶと、その期間の内訳と作業を右側の詳細に表示する。作業Issueだけを集計し、集約用のIssueは加算しない。目標別の期間の内訳では、その目標に属する作業だけを対象にする。担当者がいない作業は「未担当」にまとめる。

内訳は次の三つに分け、各作業を一回ずつ数える。

| 内訳 | 対象 |
| --- | --- |
| 作業中 | 作業中で、未解消の待ちがない作業 |
| 着手可能 | 未着手で、前提が完了し、未解消の待ちがない作業 |
| 待ち・確認 | 前提待ち、判断待ち、確認待ち、状態が未確認の作業など、上記に当てはまらない未完了作業 |

完了済みの作業は合計から除く。作業中のEstimateは全額を含め、完了条件の達成率では減らさない。未完了作業にEstimateが欠けていれば、担当者の合計と該当する内訳を「未入力」と表示する。

ポイントは実際の残り日数や稼働時間に対する負荷率を表さない。イテレーションの割当に関する扱いは、[イテレーションと期限](#イテレーションと期限)に従う。

担当者名は一つの作業に一つ設定し、前後の空白を除いて保存する。担当変更は変更前後の名前を記録し、状態、Estimate、完了条件、優先順を保持する。

## 詳細での入力と移動

各更新ボタンは、そのボタンに対応する項目だけを保存する。ほかの未保存入力は、詳細内の画面移動や更新による再描画をまたいで保持し、入力した対象を再び開いたときに復元する。詳細を閉じる、プロジェクトを切り替える、ページを再読み込みする操作で未保存入力を破棄する。

保存処理の待機中は詳細の入力を一時停止し、処理完了後に再開する。待機中に詳細を閉じても、保存結果は元のプロジェクトにだけ反映し、失敗時は保存済みデータを維持する。

担当別一覧へ戻る際は、元のイテレーション、担当者、目標の範囲を保持し、現在の作業データで集計する。

## 起動と検証

Node.jsを用意し、このフォルダで `npm start` を実行する。外部パッケージのインストールは不要で、Node.js v24.19.0で動作を確認している。  
ブラウザで <http://127.0.0.1:4319/> を開く。`PORT` 環境変数でポートを変えられる。ブラウザの保存領域はポートごとに分かれるため、別のポートでは保存したデータが見えない。ブラウザ検証は `QA_BASE_URL` で接続先を指定する。

```sh
# bash・Git Bash
PORT=4320 npm start
```

```powershell
# PowerShell
$env:PORT = '4320'; npm start
```

PowerShellで設定した `$env:PORT` は、そのウィンドウを閉じるまで残る。4319に戻すときは `Remove-Item Env:PORT` を実行する。  
`npm test` は表示判断と保存・分離・復旧・snapshot・ローカルgh・共有保存のテストを実行する。共有SQLの試験はNodeのSQLiteを使う。`npm run check` はJavaScriptの構文を検査する。

`dist/` は手書きのアプリ本体、`tests/` は表示判断のテスト、`samples/` は架空のサンプル記録を持つ。観察資料（`references/`）はGit管理しない。

Nodeテスト、構文チェック、`npm start`による起動、クラウド環境のChromiumでの操作検証を実施した。サンプルデータの表示確認と、破損・失敗を起こすQA用fixtureを区別する。どちらも専用の一時ブラウザコンテキストで行い、利用者の保存領域を変更しない。

ブラウザ検証は起動済みサーバーに対して`npm run test:browser`を実行する。ローカルアプリの起動に外部パッケージは不要。単体テストのMCP出力契約はPythonのjsonschemaを使う。任意のブラウザ検証には環境が提供するPlaywrightとChromiumを利用する。Playwrightのモジュールとブラウザの場所は環境変数で指定できる。

```sh
PLAYWRIGHT_MODULE=/path/to/playwright/index.mjs CHROMIUM_PATH=/path/to/chromium npm run test:browser
```

登録・保存とsnapshotの検証結果・画面は、既定で`/tmp/progress-tool-browser-qa/`に保存する。イテレーションの検証は、OSの一時領域に実行ごとのフォルダーを作って保存する。`QA_ARTIFACT_DIR`で保存先を指定できる。

クラウド用のビルドと隔離QAは`npm ci`後に実行する。`npm run build`、`npm run test:cloud:browser`を使う。初回取込は`npm run test:prepared:browser`、仮見積は`npm run test:estimates:browser`で操作検証する。各結果の保存先は`PREPARED_QA_ARTIFACT_DIR`と`ESTIMATE_QA_ARTIFACT_DIR`で指定できる。共有保存の結果と画面は`/tmp/progress-tool-cloud-browser-qa/`へ保存し、`CLOUD_QA_ARTIFACT_DIR`で変更できる。本番認証・D1・公開の確認とは分ける。
